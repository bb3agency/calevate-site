## 2. Milestone 1 — Client #1 Live (thin vertical slice)

Build ONLY what one client needs; admin can be CLI + SQL where UI would slow us:
- Repo: monorepo (apps/web, apps/api, apps/voice-runtime, apps/workers, packages/shared).
- DB core: organizations, users/memberships/invitations, agents(+prompt_versions,
  extraction_schemas), calls/transcript_turns/call_extractions, leads, usage_events,
  plans, consent_ledger, audit_log — with RLS from the first migration.
- VoiceEngine adapter (Bolna) + webhook receiver (source-IP-verified, idempotent —
  TRD §5) + reconciliation poller (the guarantee of record, D-31).
- Post-call pipeline: recording copy → redaction → extraction → lead upsert → metering →
  hot-lead notification (email first; WhatsApp next).
- Client app v1: login/invite accept, dashboard (calls, outcomes, sentiment), call detail
  (redacted transcript + recording + summary + extracted fields), Leads table (schema-driven
  columns, status, filters, CSV export, owner-role "Call this lead" with optional per-call
  context note — D-21; same compliance pre-checks as webhook dispatch).
- Admin v1: new-client wizard steps 1–5 minimal + test-call gate; KB upload+approve;
  publish/promote.
- Regression harness v1: the mandatory five scenarios + fixture replay + report.
- Ops: Sentry, LLM tracing, alerts that reach a person, backups, pre-launch checklist run.
  — **OpenTelemetry tracing shipped and it crosses every boundary** (BUILD-LOG §24;
  `apps/api/core/observability.py`): `TracingMiddleware` opens the server span and only
  trusts an inbound `traceparent` where the caller is ours — voice-runtime's receiver is
  reachable from the internet, and a stranger's sampled flag is a lever on our trace
  bill — and the W3C traceparent then rides the ARQ payload (`TRACE_KWARG`), so
  voice-runtime → Redis → worker → adapter → Postgres is ONE trace and "where did the two
  minutes go" is answerable. The pipeline and the webhook fast path carry named stage
  spans; span attributes are an ALLOWLIST, not a denylist, because a denylist on a
  tracing API fails open (hard rule 6). **Sentry shipped**, config-gated, with the
  `scrub_event` redaction hook that is not optional. **Langfuse and PostHog config was
  REMOVED, not wired** (D-49): three settings with no client are worse than none, because
  the next reader assumes traces are being recorded. Per-call token cost and the latency
  breakdown TRD §2 describes remain a stated gap; restoring Langfuse is a vendor decision
  plus a decision-log entry, not a wiring job — and it now inherits a REQUIREMENT rather
  than a hook: hard rule 6 is enforced by `_RedactingSpanExporter`, which every span leaves
  through, so a direct Langfuse SDK client would be a second UNFILTERED path. The
  hand-called `redact_trace_payload` this bullet used to name is deleted (D-61).
  **Alerts now reach a person** (D-49): `alert()` still writes the structured ERROR log
  first and unconditionally, and then delivers by email through the same transport as
  hot-lead notifications, with per-fingerprint repeat suppression (15 min) and a global
  token bucket, off the request path on a daemon thread and touching neither the outbox
  nor Redis. It needs `ALERTS_EMAIL` + an SMTP host to be configured; a deployment with
  neither says so at boot. **Backups: the mechanism ships, unapplied** (D-50) —
  `infra/backup/` carries wal-g continuous archiving with `archive_timeout = 300`, a
  nightly base backup, an independent offsite encrypted dump, a four-check watchdog and
  systemd timers, with every secret a reference. Nothing has been applied and no wal-g
  command has been run, so the pre-launch checklist's "backups verified" is ticked by the
  drill (`runbooks/backup-restore-drill.md`) passing once, not by this tree existing.

- **Inbound receptionist is the headline capability (D-38)** — it is Outpero's confirmed
  unbuilt flank and is consent-clean by construction (the caller initiated), so it also
  de-risks the self-serve motion. Build and demo it first.
- **Schema-for-scale (D-39):** credits/prepaid ledger, `plan_tier` on organizations, and
  invitations ship in M1 even though the self-serve UI does not — metering and tenancy
  are not retrofittable (D-12).

Gate G1: a paying client (pilot pricing allowed) live on inbound; lead-in-2-min SLO met
for 7 consecutive days; zero cross-tenant test failures.

## 3. Milestone 2 — Outbound + Multi-Client

- Campaigns end-to-end with the compliance gate (blocked features visibly explained);
  instant-lead-callback webhook ingest (Meta/website/Sheets); retry/escalation; DNC.
  — **shipped** (BUILD-LOG §30, §31, §32, §41, §47). **Escalation after retry exhaustion
  now shipped too**: a contact whose dial ladder is spent enqueues
  `escalate_campaign_contact` (registered in `WorkerSettings`, once per contact, its own
  retry ladder), which runs through `check_dispatch` itself rather than a
  messaging-shaped copy of the rules, and every non-delivery is recorded on the lead
  timeline — "we never followed up" is a fact the client can see. What it cannot do is
  send: see the WhatsApp bullet below. Meta Lead Ads ingest is now NATIVE
  (`GET|POST /hooks/v1/ingest/meta/{webhook_id}`) rather than "a webhook you could point
  at us", with one honest hole — the Graph read that carries the form answers needs a
  Page token this deployment does not hold (SURFACES §2b).
- WhatsApp follow-up + hot-lead WhatsApp alerts. — **the TRANSPORT is the single thing
  blocking a finished feature, and as of this pass it is the only thing**
  (`apps/workers/whatsapp.py`: the `WhatsAppTransport` protocol, a console dev sink, the
  delivery record and the retry ladder). This bullet used to read "still seam only",
  which was true of the transport and quietly false of everything upstream of it:
  `enqueue_hot_lead_whatsapp` had NO CALLER, so the seam was not merely unfinished, it
  was unreachable — flipping a BSP on would have delivered nothing and looked
  configured. `notify_hot_lead` now calls it on the same detection that sends the email,
  and the email dedupe carries a `channel` predicate so the two do not eat each other's
  delivery record. Deliberately NO vendor adapter: §6 contains no decision choosing a WhatsApp
  Business Solution Provider, and an adapter written against an imagined API looks
  finished. Messages are template-name + locale + positional variables — the module has no
  free-text body field at all, because a business-initiated message needs an approved
  template. What DID land is the consent the send needs: the `messaging` purpose on
  `consent_ledger` (migration `c2f7a91b4e63`) plus
  `POST /v1/compliance/messaging-consent`, because **consent to be CALLED is not consent
  to be MESSAGED** and nothing was backfilled from one to the other. So the escalation
  path is complete end-to-end except for the transport, and a contact who has opted in is
  refused today as `whatsapp_disabled` (the channel stays off until a human finishes the
  WABA/template checklist) and, once it is switched on, as `no_provider_configured`.
  Picking a BSP is a decision-log entry, and it is what unblocks this bullet.
- One-click AI callback on needs-follow-up calls (D-21): re-dispatch the agent with
  prior-call context via the engine's context-injection webhook. — **shipped**
  (BUILD-LOG §35).
- Outbound CRM sync (D-23): HMAC-signed outbound webhooks + Google Sheets sync
  (lead.created/updated, call.completed events; config table shipped in M1).
  — webhook half **shipped** (BUILD-LOG §34); **Google Sheets sync shipped**
  (BUILD-LOG §47) — `POST /v1/integrations/endpoints/sheets`, delivered through the SAME
  job as the webhook half so it reuses the delivery id, the retry ladder and the
  exhaustion alert rather than minting a second definition of "we delivered a lead", with
  column order held in a JSON array (JSONB does not preserve key order) and an event with
  no declared order REFUSED rather than guessed. **The vendor adapter is now built too**
  (`apps/workers/google_sheets.py`, `GOOGLE_SHEETS_PROVIDER=service_account`): a service
  account the client shares their own document with — chosen over an installed-app OAuth
  flow because sharing is per-document, revocable by the client without us, and holds no
  per-tenant refresh token — minting its own RS256/JWT-bearer token and calling
  `spreadsheets.values.append` with `RAW` + `INSERT_ROWS`. No SDK was added; `pyjwt[crypto]`
  and `httpx` were already in the lockfile. Sheets has NO idempotency key, so a retried job
  reads the delivery-id column before writing and reports `already_present` rather than
  duplicating a row, and a probe that cannot read refuses to write at all.

## 4. Milestone 3 — Moat Features

- Managed RAG/memory service (D-28) in the call path: in-call retrieval moves off the
  engine's built-in KB onto the provider (custom tool / thin endpoint, whichever the
  bake-off measured faster); T0 compiled-context automation; knowledge-gap report
  driving KB updates. CRM-side provider integration lands earlier (M2, with the
  bake-off).
- Regression suite growth to 50–100 scenarios/client + red-team set; client-facing QA
  report (sales asset). — **both shipped.** 110 golden cases (58 clinic / 52 real estate)
  of which 30 are red-team, across disclosure suppression, direct AND indirect prompt
  injection (OWASP LLM01:2025 — the indirect form is the one that reaches an extraction),
  PII exfiltration, DNC evasion in both directions, extraction poisoning and degenerate
  input. One executable honesty rule governs the set: `test_every_red_team_case_bites_
  without_a_model` requires each case to carry at least one assertion our own code scores
  against the real attack text, because the offline stand-in is not an LLM and a case whose
  only failure mode is "a model was persuaded" cannot be scored today. `must_not_say` stays
  reference-only until OPERATIONS §3's replay-into-call exists, and says so where a run
  enforces it. **QA report**: `make qa-report CLIENT=<slug> VERTICAL=<...>`, Markdown,
  deterministic, headlined by the DEFECT COUNT rather than a pass rate — defects map onto
  `NON_WAIVABLE_KINDS`, the one promise the harness keeps, whereas a raw pass rate against
  the offline model underclaims a client's agent. Aggregation IS the redaction (per-case
  rows would carry titles that paraphrase caller content), and `basis` follows
  `after_hours_basis`: no percentage under 12 scenarios, no trend from one month. The
  month-over-month comparison is a stated seam, not a half-wired field.
- Call-corpus embeddings (learn from resolved calls). — **not built**, and blocked by D-28:
  RAG is a managed API service and no provider is chosen.
- A/B greeting/script testing with conversion attribution. — **shipped for OUTBOUND**
  (BUILD-LOG §54). The variant a call ran is a STORED FACT written in the same transaction
  as the `calls` row, never re-derived — the split is mutable, so a read-time recompute
  silently re-attributes history the moment anyone ramps the weights. Wilson score
  intervals per arm and Newcombe's hybrid interval for the difference, with
  `MIN_CALLS_PER_VARIANT = 40` taken from Fagerland/Lydersen/Laake rather than from taste;
  below it no comparison is published at all, and only a `winner` verdict gets a badge.
  **Inbound is attributed by FACT or not at all** (D-60). `workers/pipeline.py` now
  records the arm when the engine reports that an ARM's own agent ran the call — its own
  ref, so no inference — and records nothing when it reports the agent's. An inbound
  caller reaches the client's number, which answers with the agent (FLOWS §3), so in
  today's provisioning they carry no arm; drawing a bucket for them after the call would
  credit a script they never heard. An inbound-only agent is still refused, for that
  reason rather than for a missing lookup, and `attributed_directions` is now READ from
  the assigned calls instead of being the literal `("outbound",)`. The same lookup closes
  a real outbound gap: a webhook that beat `dispatch_call`'s commit used to leave an
  arm-dialled call carrying no arm at all. Because an arm can now be credited with a call
  nobody dialled, each arm's counts are resolved by DIRECTION (D-62): `outbound_dialled`
  is the calls we placed, and `inbound_attributed` says how much of the rate's
  denominator was never split — a number, so the screen can qualify the rate it renders
  rather than leaving it to the coverage sentence.
- Client staff roles, lead assignment, lead_events timeline. — **all three shipped**
  (BUILD-LOG §53, §54). Assignment closed `Lead.assigned_to`, an `UNWIRED_BASELINE` entry
  since the first migration; the timeline PROJECTS `lead_events.payload` key-by-key rather
  than serialising a schemaless column six producers write. Staff roles complete it: a
  client owner can now invite, re-role and remove, where every membership change used to be
  an operator running SQL. The last owner cannot be removed or demoted, and the guard locks
  the whole owner SET rather than the target row — EvalPlanQual is blind to rows the query
  never selected, and a `count(*) > 1` check lets two concurrent demotions both commit to
  zero owners, which is a tenant recoverable only by hand.

Gate G3: retrieval T3 p95 ≤ 100ms measured; QA report shipped to every client monthly.

## 5. Milestone 4 — Phase-2 Engine (own orchestration) [enter only on trigger]

Trigger (pre-committed in TRD §10): sustained > ~10–15k min/month across tenants OR a
feature blocked by rented pipeline (T1/T2 tiers, custom turn-taking) OR engine risk event.
- Runtime behind the same VoiceEngine interface; Vobiz/Exotel SIP direct; models
  unchanged (Sarvam/Gemini APIs). Two candidates, decided at the gate on measured
  evidence, not now (D-32): **Pipecat on CPU droplets** (D-02's original plan; first-party
  Exotel serializer + Sarvam plugins; we build the per-call dispatcher and scale-out) or
  **LiveKit Cloud** (ap-south Mumbai region verified; first-party Sarvam plugin; turn
  detection + barge-in in-SDK; managed scaling — but concurrency tiers cap at 5/20/600
  with a 10× cost cliff past 20, and its economics only beat the alternatives above
  ~5k min/month). Both carry the same Indic caveat: **turn detection is an orchestration
  property BYOK models do not fix** — LiveKit's detector excludes Telugu and degrades to
  VAD-only; budget for endpointing work (e.g. Sarvam stt-mode) on either path.
- Shadow mode: mirror a % of calls; compare latency/quality/cost vs the rented engine via the
  regression suite + usage_events; migrate tenant-by-tenant.
Phase 3 (GPU self-host) stays parked until >~50k min/month AND open Telugu TTS reaches
Bulbul-class quality — revisit quarterly, decide on usage_events data, not vibes.
