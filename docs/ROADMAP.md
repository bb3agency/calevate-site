**client #1 live on a partly-manual stack beats a finished platform with zero clients.**

## 2. Milestone 1 — Client #1 Live (thin vertical slice)

Build ONLY what one client needs; admin can be CLI + SQL where UI would slow us:
- Repo: monorepo (apps/web, apps/api, apps/voice-runtime, apps/workers, packages/shared).
- DB core: organizations, users/memberships/invitations, agents(+prompt_versions,
  extraction_schemas), calls/transcript_turns/call_extractions, leads, usage_events,
  plans, consent_ledger, audit_log — with RLS from the first migration.
- VoiceEngine adapter (Bolna) + webhook receiver (source-IP-verified, idempotent —
  TRD §5) + reconciliation poller (the guarantee of record, D-31).
- Post-call pipeline: recording copy → redaction → extraction → lead upsert → metering →
  hot-lead notification (email first; WhatsApp next).
- Client app v1: login/invite accept, dashboard (calls, outcomes, sentiment), call detail
  (redacted transcript + recording + summary + extracted fields), Leads table (schema-driven
  columns, status, filters, CSV export, owner-role "Call this lead" with optional per-call
  context note — D-21; same compliance pre-checks as webhook dispatch).
- Admin v1: new-client wizard steps 1–5 minimal + test-call gate; KB upload+approve;
  publish/promote.
- Regression harness v1: the mandatory five scenarios + fixture replay + report.
- Ops: Sentry, Langfuse, alerts to phone, backups, pre-launch checklist run.
  — **OpenTelemetry tracing shipped and it crosses every boundary** (BUILD-LOG §24;
  `apps/api/core/observability.py`): `TracingMiddleware` opens the server span and only
  trusts an inbound `traceparent` where the caller is ours — voice-runtime's receiver is
  reachable from the internet, and a stranger's sampled flag is a lever on our trace
  bill — and the W3C traceparent then rides the ARQ payload (`TRACE_KWARG`), so
  voice-runtime → Redis → worker → adapter → Postgres is ONE trace and "where did the two
  minutes go" is answerable. The pipeline and the webhook fast path carry named stage
  spans; span attributes are an ALLOWLIST, not a denylist, because a denylist on a
  tracing API fails open (hard rule 6). **Sentry shipped**, config-gated, with the
  `scrub_event` redaction hook that is not optional. **Langfuse is a seam only** — the
  two config keys and `redact_trace_payload` exist; no client calls it, so per-call token
  cost and the latency breakdown TRD §2 describes are not being recorded yet.
  **Alerts-to-phone not built**: `core/alerting.py` normalizes the failure stage and the
  metric vocabulary, and every alert is a structured ERROR log — routable, but routed
  nowhere (OPERATIONS §4 names the sinks). **Backups not built**: D-26 makes continuous
  WAL archiving (wal-g → R2) REQUIRED rather than optional, and `infra/` carries none of
  it; it is step 9 of DEPLOYMENT §9's go-live order and blocks the pre-launch checklist.

- **Inbound receptionist is the headline capability (D-38)** — it is Outpero's confirmed
  unbuilt flank and is consent-clean by construction (the caller initiated), so it also
  de-risks the self-serve motion. Build and demo it first.
- **Schema-for-scale (D-39):** credits/prepaid ledger, `plan_tier` on organizations, and
  invitations ship in M1 even though the self-serve UI does not — metering and tenancy
  are not retrofittable (D-12).

Gate G1: a paying client (pilot pricing allowed) live on inbound; lead-in-2-min SLO met
for 7 consecutive days; zero cross-tenant test failures.

## 3. Milestone 2 — Outbound + Multi-Client

- Campaigns end-to-end with the compliance gate (blocked features visibly explained);
  instant-lead-callback webhook ingest (Meta/website/Sheets); retry/escalation; DNC.
  — **shipped** (BUILD-LOG §30, §31, §32, §41, §47). **Escalation after retry exhaustion
  now shipped too**: a contact whose dial ladder is spent enqueues
  `escalate_campaign_contact` (registered in `WorkerSettings`, once per contact, its own
  retry ladder), which runs through `check_dispatch` itself rather than a
  messaging-shaped copy of the rules, and every non-delivery is recorded on the lead
  timeline — "we never followed up" is a fact the client can see. What it cannot do is
  send: see the WhatsApp bullet below. Meta Lead Ads ingest is now NATIVE
  (`GET|POST /hooks/v1/ingest/meta/{webhook_id}`) rather than "a webhook you could point
  at us", with one honest hole — the Graph read that carries the form answers needs a
  Page token this deployment does not hold (SURFACES §2b).
- WhatsApp follow-up + hot-lead WhatsApp alerts. — **still seam only, and it is now the
  single thing blocking a finished feature** (`apps/workers/whatsapp.py`: the
  `WhatsAppTransport` protocol, a console dev sink, the delivery record and the retry
  ladder). Deliberately NO vendor adapter: §6 contains no decision choosing a WhatsApp
  Business Solution Provider, and an adapter written against an imagined API looks
  finished. Messages are template-name + locale + positional variables — the module has no
  free-text body field at all, because a business-initiated message needs an approved
  template. What DID land is the consent the send needs: the `messaging` purpose on
  `consent_ledger` (migration `c2f7a91b4e63`) plus
  `POST /v1/compliance/messaging-consent`, because **consent to be CALLED is not consent
  to be MESSAGED** and nothing was backfilled from one to the other. So the escalation
  path is complete end-to-end except for the transport, and a contact who has opted in is
  refused today as `whatsapp_disabled` (the channel stays off until a human finishes the
  WABA/template checklist) and, once it is switched on, as `no_provider_configured`.
  Picking a BSP is a decision-log entry, and it is what unblocks this bullet.
- One-click AI callback on needs-follow-up calls (D-21): re-dispatch the agent with
  prior-call context via the engine's context-injection webhook. — **shipped**
  (BUILD-LOG §35).
- Outbound CRM sync (D-23): HMAC-signed outbound webhooks + Google Sheets sync
  (lead.created/updated, call.completed events; config table shipped in M1).
  — webhook half **shipped** (BUILD-LOG §34); **Google Sheets sync shipped**
  (BUILD-LOG §47) — `POST /v1/integrations/endpoints/sheets`, delivered through the SAME
  job as the webhook half so it reuses the delivery id, the retry ladder and the
  exhaustion alert rather than minting a second definition of "we delivered a lead", with
  column order held in a JSON array (JSONB does not preserve key order) and an event with
  no declared order REFUSED rather than guessed. **The vendor adapter is the seam that
  remains**: no Google service account, no OAuth, no SDK in the lockfile, so
  `sheets_delivery_available()` is the one selector both the config route and the worker
  ask, and a deployment without it refuses the endpoint at creation rather than accepting
  rows into silence.
- Billing surfaces: usage panel (client), margin panel (admin), invoice generation,
  Razorpay links, caps UI. — usage + margin panels **shipped** (BUILD-LOG §36),
  invoice generation **shipped** (BUILD-LOG §40); the **caps-editing UI shipped**
  (client-settable `plans.client_cap_min`/`client_cap_spend`, effective cap =
  `LEAST(admin, client)`, `GET`/`PUT /v1/billing/caps`, SURFACES §2b) and the
  **value-tier rate column shipped** (`plans.overage_rate_value`; NULL = bill everything
  at `overage_rate`, which is every existing plan — **the retail number itself is an
  OPEN founder decision**, deliberately not derived from TRD §10.1's unmeasured bands).
  **Razorpay links still not built**: the payment CAPABILITY is now expressible
  (`PAYMENT_PROVIDER` + one `payment_capability()` selector shared by the intent route
  and the receiver, refusing in problem+json and writing nothing), but server-side order
  creation remains NOT IMPLEMENTED — no credentials, no adapter,
  `PROVIDER_CREATES_ORDERS` is False and `provider_order_pending` stays true
  (SURFACES §2c). Two additions since: every money reader resolves the plan **in effect**
  rather than the newest row (D-46), and ops can re-derive a stuck cap flag —
  `POST /v1/ops/tenants/{tenant_id}/spend-cap/recompute`, which recomputes and never
  writes the flag directly, closing the dead end where a client raised past their ceiling
  stayed stopped until they acted themselves or the IST month rolled over.
- Admin polish: onboarding wizard complete, client health overview, prompt rollback UI.
  — client health overview and prompt rollback UI **shipped** (BUILD-LOG §33, §40,
  §41). The **intake step shipped as an API** (BUILD-LOG §45;
  `GET|POST /v1/admin/tenants/{tenant_id}/agents/{agent_id}/intake`, FLOWS §1's eight
  fields and no invented ninth, writing the `compiled_t0_context` D-39 had reserved) —
  but the WIZARD still shows only steps 1 and 8: intake, number provisioning and the
  test-call gate are absent from `/admin/new` rather than stubbed, the last two because
  they are pilot-gated.
- Vertical template #2 fully dressed (whichever client #2 is: clinic or real estate).
  — **real estate shipped** (not written up in the BUILD-LOG; the artefacts are the
  evidence): the `VERTICAL_TEMPLATES["real_estate"]`
  extraction schema AND the half that makes it a template rather than a column list —
  its own `re_*` golden transcripts covering the mandatory five, with
  `tests/vertical_real_estate_test.py` failing when schema and fixtures drift apart. A
  field nothing scores is a column no model is ever measured on.

- **Self-serve tier goes live (D-34):** signup + Google OAuth, credit top-up, number
  purchase with KYC gate. Ships WITH its R-11 mitigations — fixed calling hours, DNC on
  every path, mandatory disclosure, consent ledger, spend caps, and manual review of each
  account's first campaign. No self-serve calling before those exist.
  — signup, the top-up intent and the payment receiver **shipped as surfaces, not as a
  checkout** (SURFACES §2c: `self_serve_signup_enabled` defaults OFF, and server-side
  order creation is not built). **KYC shipped** (D-47) — the last mitigation that had
  nothing behind it. Of the R-11 list, five hold in code today (platform-fixed calling
  hours in `within_calling_hours`, DNC on every dispatch path, NOT NULL disclosure, the
  consent ledger, admin + client spend caps) and **the sixth does not: nothing holds a
  self-serve account's FIRST campaign for manual review** — no flag, no queue, no
  blocker. `tenancy/signup.py` names the requirement in prose. That is the gap to close
  before the signup switch is turned on.
- Integration DX (SURFACES §2b): webhook activity view, test-webhook, "Needs attention"
  queue, two-speed publishing. — activity view, test-webhook and the attention queue
  **shipped** (BUILD-LOG §37, §38, §39); **two-speed publishing shipped** (BUILD-LOG §47)
  — admin `POST …/apply` (staged version as the CAS token) and `POST …/undo`, the
  per-agent call cap on the same page, and the client-side unsaved-changes banner read
  from `GET /v1/agents/{agent_id}/pending`. Pending is DERIVED from two pointers, never
  stored as a flag that can disagree with them.

Gate G2: 2–3 clients incl. one outbound campaigner; DLT template approved and a
compliant campaign completed; margin per client visible and ≥ target.

## 4. Milestone 3 — Moat Features

- Managed RAG/memory service (D-28) in the call path: in-call retrieval moves off the
  engine's built-in KB onto the provider (custom tool / thin endpoint, whichever the
  bake-off measured faster); T0 compiled-context automation; knowledge-gap report
  driving KB updates. CRM-side provider integration lands earlier (M2, with the
  bake-off).
- Regression suite growth to 50–100 scenarios/client + red-team set; client-facing QA
  report (sales asset).
- Call-corpus embeddings (learn from resolved calls).
- A/B greeting/script testing with conversion attribution.
- Client staff roles, lead assignment, lead_events timeline.

Gate G3: retrieval T3 p95 ≤ 100ms measured; QA report shipped to every client monthly.

## 5. Milestone 4 — Phase-2 Engine (own orchestration) [enter only on trigger]

Trigger (pre-committed in TRD §10): sustained > ~10–15k min/month across tenants OR a
feature blocked by rented pipeline (T1/T2 tiers, custom turn-taking) OR engine risk event.
- Runtime behind the same VoiceEngine interface; Vobiz/Exotel SIP direct; models
  unchanged (Sarvam/Gemini APIs). Two candidates, decided at the gate on measured
  evidence, not now (D-32): **Pipecat on CPU droplets** (D-02's original plan; first-party
  Exotel serializer + Sarvam plugins; we build the per-call dispatcher and scale-out) or
  **LiveKit Cloud** (ap-south Mumbai region verified; first-party Sarvam plugin; turn
  detection + barge-in in-SDK; managed scaling — but concurrency tiers cap at 5/20/600
  with a 10× cost cliff past 20, and its economics only beat the alternatives above
  ~5k min/month). Both carry the same Indic caveat: **turn detection is an orchestration
  property BYOK models do not fix** — LiveKit's detector excludes Telugu and degrades to
  VAD-only; budget for endpointing work (e.g. Sarvam stt-mode) on either path.
- Shadow mode: mirror a % of calls; compare latency/quality/cost vs the rented engine via the
  regression suite + usage_events; migrate tenant-by-tenant.
Phase 3 (GPU self-host) stays parked until >~50k min/month AND open Telugu TTS reaches
Bulbul-class quality — revisit quarterly, decide on usage_events data, not vibes.

| D-44 | **The erasure record stops being the last copy of the number**: `deletion_requests.phone_e164` is cleared on completion and `subject_ref` takes over | Migration `f4a8e1c07b62`. `subject_ref TEXT NOT NULL` (sha256 of the number, hex, first 32 chars) is backfilled, then `phone_e164` drops NOT NULL and every completed row is cleared. | D-45 | **An ops step-up confirmation names the TRANSITION, not the endpoint** | `X-Confirm-Action` on `POST /v1/ops/platform` must echo the exact move being made: `halt_outbound`, `release_outbound`, `set_load_shed:<mode>`, or — for a request that does both — the two joined in a fixed order (`halt_outbound+set_load_shed:reduced`). | D-46 | **A tenant's plan is the row whose EFFECTIVE WINDOW contains the instant** — not the newest row | `plans.effective_from` / `effective_to` become the row's valid time, resolved through one helper (`billing/plans.plan_in_effect_sql`) that every money reader now calls: the derived invoice, the usage panel, both cap reads, the worst-case call-cost quote and the dispatch concurrency ceiling. So overlap is resolved deterministically rather than forbidden, and the order has two properties worth stating: a dated row beats an undated one once it comes into effect (so the ordinary gesture — leave the old windowless row alone, INSERT the new terms with a start date — is correct without a second statement), and **with every window NULL the order collapses to `created_at DESC, id DESC`, the newest-row rule this repo already had — so this re-prices nobody on the day it lands.** The `id DESC` tail is the same load-bearing tail as `ix_credit_ledger_tenant_recent`: "newest" has to be a TOTAL order or two readers disagree about which row it is, and two rows inserted in one transaction share a `created_at`. **The consequence recorded rather than discovered:** an operator who sets `effective_to` on a live plan WITHOUT inserting a successor drops that tenant's ceiling and overage rate at that instant, silently.
