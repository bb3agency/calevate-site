## Method and scope

I followed the journey from the alarm email back to the screens it names. The email quotes
`runbooks/alarm-index.md` at send time (`core/alert_email.compose_alert`), so a wrong screen or
button in that file is a wrong instruction in a page mail. Four checks ran across every runbook:

1. **Console paths.** Every console path written as code in `runbooks/*.md` was resolved against
   the App Router tree, with dynamic segments handled. This check is now a test.
2. **API routes.** Every `/v1/...` route named in a runbook was checked against
   `apps/web/src/lib/api/openapi.json`. The webhook, `/reports` and `/v1/worker` routes were
   checked by hand. All exist.
3. **Labels.** Every bold or quoted control label in the runbooks was checked against the
   web source and the ops settings catalogue (`ops/config_catalog.py`). This included labels
   that wrap across a line break.
4. **Scripts.** Every `python -m scripts.*` command in a runbook was checked for the script
   and its argparse arguments.

I also ran two cross-cutting scans:

- **Audit coverage.** An AST scan of every admin and ops mutating route for an audit write,
  following three levels of calls. Every hit was a client route or a refusal.
- **Half-wired seams.** Every exported web hook with no caller, and every admin or ops route
  that no web code names.
