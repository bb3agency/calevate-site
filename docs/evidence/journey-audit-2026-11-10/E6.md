## Not fixed

**Not proven: Docker Desktop stopped before the test could run**
- **P3, `workers/number_rental.renew_number_rentals`.**
  - The `_RENEWING` list is read once per tenant, and each number is collected later without being re-read.
  - A number released or held in between is charged a full period. This is idempotent per period, so it is never doubled.
  - Planned fix: at the top of each per-number transaction, a `SELECT ... FOR UPDATE` re-reads `released_at IS NULL AND NOT held`, and the number is skipped when that no longer holds.
  - The test is written; it was taken out of the committed file because it never ran.

**Reported by the sub-sweeps and not proven by me: UNVERIFIED**
- **P3, `owner_digest.send_owner_digests`.**
  - It walks every opted-in org with no `WalkBudget`.
  - Past the 300 s arq timeout the job ends for good (fleet_walk's docstring explains why), so the tail misses that day's digest.
  - The fix is the `trial_notices` pattern.
- **P3, `campaign_archive_notice`.** A terminal (non-`Retry`) error after the emails went out is re-published as `attempt == 1`. That posts a second in-app notice and sends the emails again.
- **P3, outbox re-publish in general.** Every send-then-record job re-sends two hours later if the record fails. The ones named are `notifications.notify_hot_lead`, `whatsapp.notify_hot_lead_whatsapp`, `escalate_campaign_contact` and `team_alerts.deliver_team_alert`. This is the documented at-least-once trade.
- **Lock held across a vendor call.**
  - **P3, team alert delivery:** `team_alerts.deliver_team_alert` holds `FOR UPDATE OF ta` across the email or WhatsApp send.
  - **P3, number purchase:** it holds the `credit:<tenant>` advisory lock across a vendor GET/PATCH, or a move, because `record_engine_number` calls `collect_number_rental` and then `sync_number_attachment`. Every charge for that tenant waits on it.
- **Out-of-order or stale writes.**
  - **P3, drift sweep:** `engine_reconciliation._repair_own_voice_key` repairs from a `drift` read several vendor round trips earlier, so a Clear/Studio publish in between can be set back.
  - **P3, key rotations:** `studio_voice_key`, `own_model_key` and `voice_comparison_key` read the key and then install it. Two rotations seconds apart can land out of order, and the readiness checks do not compare key identity.
  - **P3, call lines:** `engine_workspaces` call-lines sync is last-writer-wins, and the daily sweep repairs it.
- **Crash between a vendor call and its commit.**
  - **P3, `move_into_client_workspace` and `forget_engine_number`:** if the worker dies after the vendor move and before the commit, the row keeps a stale handle.
  - **P3, `number_holds`:** if the vendor DELETE succeeds and the commit is lost, and a top-up then lands, renewals are charged for a number the vendor already released.
- **P3, campaign concurrency slider.** `_plan_tenant` sets `slots = min(slider, tenant_budget)` and does not subtract the campaign's own calls in flight. "Up to N at once" therefore climbs to the tenant ceiling. The platform pool still holds.
- **P3, `forwarding/testing.py`.**
  - Every `ProblemError` from a leg (including `engine_unreachable` on a read timeout) is taken as "not placed", without `dial_was_not_placed`.
  - A non-`ProblemError` from leg 2 after leg 1 rang leaves the test `placing`.
- **P3, `resolve_campaign_contact`.** A late pipeline result for an old call can settle a newly claimed contact, because the claim does not clear `last_call_id`. Never a second ring.

**Partly closed**
- **E6-03:** the success arm still double-dials if the request is cancelled (`CancelledError` on a deploy), or if the final COMMIT itself fails after the dial. Closing it fully needs an IN_DOUBT inbox state committed before the dial (BACKEND-PATTERNS §4).
