## Language handling, read and found sound
- Engine language: every agent is `auto` on the wire (`thinnest.py`, founder rule, memory 3e8f727b). D3 covered this, so I did not redo it.
- Language names for owners come from one registry (`calevate_shared/languages.py`, `lib/agentState.LANGUAGE_NAMES`, `callReview.languageName`). The transcript, call summary and opening line carry `lang`.
- CSV export: the BOM is added in the browser (`lib/csvDownload.ts`, `TransactionsTab.tsx`). The server writes clean UTF-8 with a formula guard (Y10-09). Pip chart CSV goes to the clipboard, so it needs no BOM.
- Email headers go through `EmailMessage` (`core/transport.py`), which encodes non-ASCII. WhatsApp parameters already handle Meta's 132018 rule (`actions/whatsapp.py:410`).
- Lengths: Telugu and Devanagari are BMP, so UTF-16 `maxLength`, Pydantic `max_length` and Postgres character counts agree. Byte budgets (`MAX_BODY_BYTES`) use `TextEncoder`.
- There is no server PDF: invoices print from the browser.

## NOT FIXED
- P3 UNVERIFIED: no Unicode normalisation (NFC) before lead search. Telugu has a canonical decomposition (U+0C48 = U+0C46 U+0C56), so an NFD-typed query could miss an NFC name. I did not observe a keyboard that emits NFD.
- P3: `components/arc/money-input.tsx` accepts ASCII digits only. These inputs use a numeric keypad (`inputMode`), which types ASCII, so I left them.
- P3: string cuts such as `[:80]` and `[:200]` (for example `script_proposals.py:993`, `starters.py:440`) slice by code point and can split a Telugu consonant from its vowel sign. Display-only.
