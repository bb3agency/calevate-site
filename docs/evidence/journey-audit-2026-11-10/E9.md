## Fixed

### E9-01 (P3): Pip's "answering" mark crossed accounts for a person in two accounts

- Where: `apps/api/copilot/live_sync.py::answering_key` (was
  `calevate:copilot:answering:{realm}:{owner_id}`), read by `copilot/routes.py::
  load_copilot_conversation` and written by `copilot/routes.py::ask_copilot`.
- Scenario: one person is a member of account A and account B (self-serve lets one person
  open several businesses; invitations add people to more). A client conversation is one per
  person PER ACCOUNT: `copilot_conversation_turns` is a FORCE-RLS tenant table and
  `transcript.load` runs under the account's tenant session. The Redis set saying "a run is
  in flight" was keyed by the person only. Asking Pip in A made B's panel (`GET
  /v1/copilot/conversation` with `X-Org-Slug: B`) answer `answering: true`, so B showed
  "Pip is thinking…" (`components/copilot/CopilotPanel.tsx`, `answeringElsewhere`) for a
  question B's conversation does not hold and whose answer never lands there. No content
  crossed (the turns list stayed B's), but one account's state appeared in another's screen.
- Fix: the client realm's key carries the account (`...:client:{account}:{owner}`);
  `answer_started` / `answer_settled` / `is_answering` take a required keyword `account`
  (None for the admin realm, whose conversation is one per operator; `viewing_tenant_id` is
  context there, not a scope). A client key without an account raises rather than silently
  merging accounts again.
- Tests (`tests/journey_audit_e9_test.py`):
  - `test_pip_answering_in_one_account_is_not_shown_in_the_persons_other_account`: two
    accounts, one person in both, a real `/v1/copilot/ask` stream in A; mid-run A reads
    `answering: true` and B must read `false` with no turns. FAILED on the old source
    (`AssertionError: account B's panel showed account A's question`, run with
    `apps/api/copilot/` checked out at HEAD~1), passes now.
  - `test_a_client_answering_mark_cannot_be_written_without_its_account`.
  - `tests/copilot_live_sync_test.py` call sites moved to the new signature.
- Commit: `fb8ef9516` plus the formatting/report commit after it.

### Redis keys and arq job ids

Every module that touches Redis (49 files) was grepped for its key builders. Tenant-scoped
state carries the tenant or a globally unique id: retrieval cache (`retrieval:q:v1:<tenant>:`,
tenant first, never hashed), voice preview counter, Pip fair-use alert, core labels lease,
export tickets (body binds tenant + person, checked on `GETDEL`), step-up proofs (digest of
an action string that names the slug), OAuth state (signed `sub`=tenant, `act`=person, checked
at callback, one-time `SET NX`), in-call once/lookup keys (vendor call ref, agent ref),
per-call action limit (`tool.id` + call ref), live channels (`calevate:live:tenant:<id>`,
person channel carries only the `conversation` topic and no data). arq job ids are built from
uuid_v7 row ids, outbox message ids, vendor execution ids or engine handles that carry their
workspace, so no two tenants can collide. The one key that was per person where the data is
per person-per-account is E9-01.

### Object storage and signed URLs

`apps/workers/storage.py` key builders all start with the tenant
(`recordings/<tenant>/…`, engine payloads, KB objects, KYC documents) or a person scope
(Pip uploads). There is no browser-side presigned PUT. Every presigned GET
(`crm/routes.get_recording`/`download_recording`, `integrations/service._recording_url`,
`kb/uploads.original_download`) presigns a key read from a tenant row under that tenant's
session; KYC documents are decrypted in memory and never presigned.

### In-process caches

Every `lru_cache` / `functools.cache` / module cache in `apps` and `packages` was read: all
are keyed by non-tenant inputs (starter templates by vertical, rate breakevens by figures,
regexes, settings, the S3 client) and hold no tenant data. The load-shed status cache holds
platform state only.

### Web (TanStack Query)

`apps/web/tests/queryKeys.test.ts` already scans every `useQuery({…})` and requires the org
slug on client-realm keys; the other entry points it does not scan were checked by hand:
every client `useInfiniteQuery` hook (`billingHistory`, `followUps`, `hooks.callsLog`,
`leads` timeline, `ownNumbers`) and every client `setQueryData` key carry
`session.orgSlug`; `engineCatalogue` carries `client:<slug>` as its audience. View-as
sessions set `orgSlug` to the viewed slug (`lib/api/admin.viewAsSession`).

### Engine (D-693)

`engine/thinnest_workspace.workspace_headers` is the only builder of the workspace header;
it refuses a tenant-only route without a customer workspace (except the two named
developer-workspace contexts, trial agent create and tenant-erasure contact lookup), refuses
a developer-only route with one, and refuses a header naming a non-customer workspace.
`workspace_of` refuses a handle of one workspace used inside another. Every ThinnestAI client
module (`thinnest`, `thinnest_actions`, `thinnest_agent_model`, `thinnest_customer_data`,
`thinnest_customers`, `thinnest_numbers`, `thinnest_webhooks`) builds headers through it.

### Outbound destinations, payments

Outbound webhooks are loaded under `tenant_session(payload tenant)` from our own outbox
(`workers/outbound_webhooks.deliver_outbound_webhook`); member emails are resolved through
RLS'd `memberships`; Razorpay credits verify tenant and amount against our order route
(`billing/payment_objects.verify_order`), tokens resolve through their own route, the
callback binds order to tenant (D-735).
