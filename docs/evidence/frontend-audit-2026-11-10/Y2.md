# Y2: Pip, client side (frontend audit round 5, 10 Nov 2026)

Scope: `components/copilot/**`, `lib/copilot/**`, `app/c/[slug]/assistant/**`,
`app/c/[slug]/ai-assist/**`. Base 8387d8b5f. The script builder (Y1) and the admin Pip (Y8)
were not touched.

## The founder's two complaints, checked against the current code

- **Text-heavy empty state:** already fixed in 0400e7802 (9 Nov). The panel is now one question
  ("What can I help with?"), up to three suggestion chips and the ask box. The skeleton shows
  instead of the empty state while the conversation loads (W4-01). No change was needed.
- **Long tasks failing with a stale failure message:** still wrong in four ways, all fixed
  below. A step stayed "running" after the answer ended (Y2-01). A script suggestion card
  showed the previous request's failure as its own (Y2-02). A background task's card
  disappeared when the drawer closed (Y2-03). Closing the drawer during a long answer aborted
  the run (Y2-06). Two related stale messages were also fixed: "could not be loaded" shown over
  a loaded conversation (Y2-04), and a whole workspace tab replaced by an error after one failed
  poll (Y2-05).

## Fixed

Each test below fails on the old source and passes on the new.

### Y2-01 (P2) The step spinner kept going after the answer was cut off or stopped
- **Where:** `lib/copilot/useCopilotConversation.ts`, in the `.then`/`.catch` of `ask` and in
  `stop`. Rendered by `StepList.tsx`, which draws every `running` step with a spinner.
- **What the user saw:** a long request ("go through all my leads") was cut off by a dropped
  connection, an error frame or Stop before the step's terminal frame arrived. "Searching your
  leads…" then kept spinning forever beside "The answer stopped part-way". Pip looked busy on a
  task that was no longer running.
- **Fix:** `settleSteps` turns any still-`running` step into `failed` when the exchange ends.
  The list then reads "Could not finish what it tried".
- **Commit:** ad9507964
- **Tests:** `tests/copilot.test.tsx`
  - "STOPS THE SPINNER when the answer is cut off mid-step…"
  - "…when the person presses Stop mid-step"

### Y2-02 (P2) A script suggestion card showed the previous request's failure as its own
- **Where:** `components/copilot/ProposalCard.tsx`, `ScriptSuggestionProgress`.
- **What the user saw:** Pip's drawer sits over the Script tab, which already holds the last
  suggestion, often a failed one. After the owner confirmed a new suggestion, the card read the
  cached proposal at once. It said "Could not write the suggestion" with the old note until its
  own read landed, and announced that through `role="status"`.
- **Fix:** the card shows "Writing the suggestion…" until its first read after mounting has
  landed (`isFetchedAfterMount`).
- **Commit:** 7cef16508
- **Test:** `tests/copilot.test.tsx`, "never shows the LAST suggestion's failure as this one's
  while its first read is on the way".

### Y2-03 (P2) A background task's card vanished when the drawer closed
- **Where:** `lib/copilot/useCopilotConversation.ts`. `jobs` was component state, and the
  dock unmounts the panel on every close and on every screen change.
- **What the user saw:** the answer says "Started in the background. Progress shows here as it
  happens." After closing and reopening Pip, there was no card, no progress and no Stop.
- **Fix:** the jobs this tab started are held per account and realm, in module scope next to
  `openOffers`. Start again forgets them. Each card still reads its state from the server.
- **Commit:** d23794eb6
- **Test:** `tests/copilot.test.tsx`, "KEEPS FOLLOWING THE BACKGROUND JOB after the panel is
  closed and opened again".

### Y2-04 (P3) "Your earlier messages could not be loaded" shown over a loaded conversation
- **Where:** `lib/copilot/useCopilotConversation.ts`. The old check was
  `historyUnavailable = Boolean(stored.error) || !stored.data`.
- **What the user saw:** a re-read failed while the conversation was already on screen. The
  re-read runs after every exchange, on every live note and on focus. When it failed, TanStack
  kept the data and set `error`, and the panel claimed the messages could not be loaded with the
  messages right below.
- **Fix:** the line now depends only on `!stored.data`. A failed first read or an offline read
  still shows it.
- **Commit:** 394863613
- **Test:** `tests/copilotConversation.test.tsx`, "DOES NOT SAY the earlier messages could not
  be loaded while they are on screen".

### Y2-05 (P2) One failed poll replaced a whole workspace tab with an error
- **Where:** in `components/copilot/workspace/`:
  - `TasksList.tsx`: the task list, and its Plans section;
  - `ApprovalsInbox.tsx`;
  - `ActivityLog.tsx`.
- **What the user saw:** these lists poll every 3 to 15 seconds while a task or plan runs. One
  failed poll swapped the running task (with its Stop), the running plan, the approvals waiting
  or the activity log for an error box. Polling went on, so the tab flickered between the two.
- **Fix:**
  - The error replaces the content only when nothing has loaded yet.
  - The Tasks tab keeps its list and shows the refusal above it.
  - Plans read `plans.data` instead of `isSuccess`.
- **Commits:** 1ccb773d8 (tasks), e83a36e28 (plans, approvals, activity)
- **Tests:** `tests/copilotWorkspace.test.tsx`
  - "keeps the running task on screen rather than replacing the whole tab with a failure"
  - "keeps a running plan on screen"
  - "keeps the approvals waiting on screen"
  - "keeps the activity log on screen"

### Y2-06 (P1, dead end on long tasks) Closing the drawer while Pip answered aborted the run
- **Where:** `components/copilot/CopilotDock.tsx` unmounted `CopilotPanel` on every close. The
  hook's unmount effect then aborts the request, and the server cancels the run when the client
  goes away (`fastapi.routing` SSE task group, uvicorn ASGI spec 2.3, `listen_for_disconnect`).
- **What the user saw:** a long request is exactly when an owner closes the drawer to get on
  with the page. Reopening showed the question with the answer cut off or missing, and nothing
  saying why.
- **Fix:** closing while an answer is arriving keeps the panel mounted with `hidden`, so the
  request goes on.
  - **What stays the same:**
    - It is still unmounted when the screen changes, because the conversation is about the old
      screen's fields.
    - It is unmounted when closed again with nothing arriving.
  - **What changed in the panel:**
    - New props: `hidden` and `onAskingChange`.
    - While hidden, it takes no Escape or Tab keys and does not move focus.
    - While hidden, it does not navigate. A destination waits until the drawer is opened again.
  - **What reopening shows:** the whole answer, and any fill with its Undo.
- **Commit:** b8d8faf17
- **Test:** `tests/copilot.test.tsx`, "KEEPS THE ANSWER GOING and shows all of it when the
  drawer is opened again". It asserts that the ask's AbortSignal is not aborted.

## Not fixed

- **The same abort on the assistant page (P2).** On `/c/[slug]/assistant`,
  `components/interior/tabs.tsx` keys the tab panel by its value (`key={tabs.value}`). Switching
  from Conversation to Tasks, which the "Running now" tile does, unmounts `CopilotPanel` and
  aborts a long answer in the same way as Y2-06. A fix needs a `keepMounted` option on the
  shared `Tabs` (Y10's component). Copying its tab list into `AssistantWorkspace` would make two
  ways of doing tabs. **Reported to Y10.**
- **A screen change still aborts an answer in flight (by design).** The dock unmounts the panel
  when the surface changes, because a fill would land on a form that is gone. Unchanged.
- **Pip's consent: a 409 `copilot_consent_outdated` (P3), not changed.** The server's own
  remediation ("Close Pip, open it again…") works: the remount refetches the conversation with
  the new words. Not a dead end.
- **JobCard poll errors (UNVERIFIED as a user-visible problem).** `JobCard` still shows a poll
  failure beside a valid card. It clears on the next successful poll, so it was left alone.
- **Pip says it is thinking after a run fails (UNVERIFIED).** The panel re-reads the
  conversation as soon as the error frame arrives. If that read reaches the server before
  `answer_settled` clears the mark, "Pip is thinking…" can show under the error. The
  `answer_settled` live note corrects it within a second while the live stream is up. Not
  reproduced.
