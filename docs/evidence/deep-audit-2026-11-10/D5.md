## Findings fixed

### D5-01 (P3, round-4 X3 open item): a description that returned to an earlier one was never written for again

- Where:
  - `apps/api/agents/starter_plans.py::maybe_write_starter_steps` keyed
    `enqueue_outbox_once` on `starter-steps:{tenant}:{digest}`.
  - `apps/api/tenancy/profile_wording.py::_queue` keyed it on
    `profile-wording:{tenant}:{digest}`.
  - `apps/api/teach/questions.py::_queue_draft` keyed it on
    `draft_teach_question:{tenant}:{key}:{fingerprint}`.
  - Outbox keys are spent for good.
- Failure:
  - An owner whose services list went A, then B, then back to A kept B's job steps and B's
    form wording. Their outbox key for A had already been used, so nothing was queued, and
    the steps named a service the business no longer sells.
  - A teach question whose inputs returned to earlier ones (a taught fact added and then
    removed: the inputs marker counts only facts not removed) had its row reset to `queued`
    for the old fingerprint, but no job came. "Drafting" showed for 15 minutes, and after
    that the draft was simply gone.
- Fix:
  - Steps and wording: each worker write now appends a `written_at` stamp
    (`starter_plans.STAMP_WRITE_SQL`). The ask is keyed on the description plus the stamp of
    the copy on file (`starter_plans.ask_key`), so asks repeated before the draft lands
    still queue one job, and any later write makes the next ask fresh.
  - Readers ignore the extra key: `plans_from_row` iterates job names and `_from_row` reads
    `wording` and `known`.
  - Teach drafts: the `teach_questions` upsert is the dedupe. It writes only when the
    fingerprint differs, `RETURNING id` gates a plain `enqueue_outbox`, and a concurrent
    read waits on the row lock and then writes nothing.
- Remaining gap, by choice: a run that fails without writing leaves its key spent until
  another write happens. Steps and wording already say "no retry, the next change asks
  again".
- Tests, all three failing before the fix:
  - `test_steps_return_to_an_earlier_list_are_written_for_it_again` (the third ask returned
    False).
  - `test_wording_return_to_an_earlier_description_is_written_for_it_again`.
  - `test_a_teach_draft_is_queued_again_when_its_inputs_return_to_earlier_ones`, which
    failed with `assert 4 == 6`.
- Commit `766fa1384`.

## Checked and found sound (not re-reported)

- **A deploy with a migration fails safe.**
  - Migrations run from the new image before any swap. `alembic/env.py` uses
    `transaction_per_migration=True`, and there is no automatic downgrade.
  - The ERR trap names the step.
  - The `--expected-sha` guard compares the full HEAD against the given value and dies on
    any difference, so an abbreviated sha fails closed.
- **Rollback.**
  - `--checkout <sha>` accepts hex only and leaves the checkout detached. A later pull
    refuses rather than undoing the rollback.
  - An existing `calevate/app:<sha12>` image is reused, not rebuilt.
  - `rolling_back_onto_a_newer_database` skips `upgrade head` and the seed only on the
    checker's clean exit 3, and requires the `alembic current` line to be a 12-hex revision.
  - Outbox rows stamped `min_revision` wait for an image that knows them (L5-04).
- **Health checks.**
  - api and voice-runtime are polled on `/healthz`, which checks the database and Redis,
    for 180 s.
  - workers and workers-bulk must stay `running 0` for `SETTLE_S`.
  - The web tier is polled on `/`.
  - Redis is brought up without `--no-deps` before the swaps.
- **Drain.**
  - The main worker's `job_completion_wait` is 45 s, under its 60 s grace.
  - The bulk worker's is 300 s (= `WORKER_JOB_TIMEOUT_S`), under its 330 s grace.
  - `TICK_LEASE_TTL_S` is 330 s, longer than the 300 s job timeout.
  - The healer's `CLAIM_LEASE_S` of 300 equals the timeout, but `advance` CASes on state
    and attempts, not on the lease (`healer/incidents.claim_due`).
- **Log redaction.** No log call passes a phone, email or transcript field, and the
  formatter scrubs the message, the extras and the exception text.
- **Systemd units.** The IST `OnCalendar` values, `Persistent=true` and the
  `OnFailure=...@%n` relay are as `infra/backup/README.md` describes.
- **CLAUDE.md.** All 35 symbols and paths it names exist where it says, and every
  `gemini-3.*` is `selectable=False`. The `make` targets (`coverage-ratchet`, `db-reset`,
  `redis-reset`, `web-check`, `dev-otp`) and the `types` CI job exist.

## Sources

- systemd.time(7), read 10 Nov 2026:
  https://www.freedesktop.org/software/systemd/man/latest/systemd.time.html. A calendar
  event may end with an IANA time zone ("weekly Pacific/Auckland"), so `OnCalendar=*-*-*
  02:30:00 Asia/Kolkata` is valid.
- systemd.unit(5), read 10 Nov 2026:
  https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html. `%n` is the
  "Full unit name" and `%N` is the same with the type suffix removed. So the backup alert
  instance is `calevate-basebackup.service`, which `notify.sh` reports as `unit=%i`.
  Valid, just verbose.
- arq docs, read 10 Nov 2026: https://arq-docs.helpmanual.io/. `job_completion_wait` is the
  "time to wait before cancelling tasks after a signal"; the worker picks no new tasks while
  waiting. The default of 0 cancels at once, and a cancelled job stays queued to run again.
