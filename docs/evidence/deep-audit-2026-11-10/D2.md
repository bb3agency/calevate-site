## Findings (all fixed in c5b64e471; each test failed before the fix)

### D2-01 (P1, money/availability): one unattributable Razorpay event could disable the whole webhook

- **Where:** `apps/api/billing/payment_routes.py::razorpay_webhook`.
- **Problem:** a signed `refund.processed` / `refund.failed`, or a captured payment, with no
  `notes.calevate_tenant_id` (and, for a payment, no order route) was refused with 422
  `payment_tenant_unresolved`.
- **Why it matters:** Razorpay counts any non-2xx as a failure, retries for 24 hours, and
  "If the webhooks continue to fail for 24 hours, the webhook is disabled"
  (https://razorpay.com/docs/webhooks/best-practices/, read 10 Nov 2026). A redelivery never
  gains our note, so the refusal is permanent. After that, every top-up credit, mandate and
  dispute event stops arriving until someone re-enables the webhook in the dashboard.
- **Who sends such events:**
  - Razorpay states "Refunds webhook events are also triggered for auto-refunds", which
    are automatic refunds of uncaptured payments
    (https://razorpay.com/docs/webhooks/refunds/, read 10 Nov 2026). Refund notes are
    ours only on refunds we issue (`create_refund`).
  - Refunds issued from the Razorpay dashboard
    (https://razorpay.com/docs/payments/refunds/, read 10 Nov 2026).
  - Payment links.
- **Fix:** `payment_tenant_unresolved` is acknowledged with 200 `status: "unattributed"`
  after the existing `razorpay_money_unapplied` page.
  - The daily reconciliation already lists these as `refund:<id>` / `unattributed:<id>`.
  - It never debits a wallet that holds no top-up for the payment.
  - I rejected resolving the tenant from the payment's order route in the webhook. That
    would have debited a wallet for an auto-refunded, never-credited payment.
- **Tests:**
  - `tests/razorpay_events_test.py::test_a_verified_payment_we_cannot_attribute_raises_an_alarm`
  - `::test_a_refund_without_tenant_notes_is_acknowledged_and_moves_nothing`
  - `tests/self_serve_test.py::test_a_payment_for_an_unknown_tenant_credits_nothing`
    (updated).
- **Closes:** Z1 UNVERIFIED. It is now verified from the vendor docs.

### D2-02 (P2, compliance/data): a contact upload racing a launch landed unscrubbed under a running campaign (Z2-N3)

- **Where:** `campaigns/service.py::add_contacts` and `::launch_campaign`.
- **Problem:** the upload read `status` unlocked. Its FK insert takes only KEY SHARE on
  `campaigns`, which does not conflict with the launch's NO KEY UPDATE. So both proceeded.
- **Measured outcome:** campaign `running` while the uploaded DNC number stayed `pending`,
  missing both the launch scrub and the confirmed count.
- **Fix:** `add_contacts` reads `FOR SHARE`, and `launch_campaign` takes `FOR UPDATE` on the
  campaign before its gate read. Lock order is agent (share), then campaign, the same order
  the recurring tick uses.
- **Test:** `tests/deep_audit_2026_11_10_d2_test.py::test_a_contact_upload_racing_a_launch_is_never_left_unscrubbed`.

### D2-03 (P2, compliance): a re-driven tenant erasure ran every arm again and rewrote the certificate (Z9-N3)

- **Where:** `apps/workers/retention.py::execute_tenant_erasure`.
- **Z9's premise was wrong.** Z9 assumed a concurrent copy "would fail on the
  `organizations.deleted_at` rowcount invariant and roll back".
- **Measured instead:** the copy read `completed_at` NULL, ran the whole erasure
  (object-store deletions included) and returned a fresh proof, not `already_completed`.
- **Fix:** read the request `FOR UPDATE`, as `execute_deletion_request` does since Z9-01.
- **Test:** `::test_a_redriven_tenant_erasure_meeting_the_original_runs_once`.

### D2-04 (P2, money): a late call of a retired engine route was metered at the replacement's rate (Z3-N1)

- **Where:** `billing/engine_minutes.py::engine_minute_cost`.
- **Problem:** it ordered the agent's routes `active DESC`, so a call of a copy that was
  recreated on another rung was priced at the new copy's rate key.
- **Fix:** an `engine_agent_ref` argument ranks the call's own route first. The pipeline
  passes `snapshot.engine_agent_ref`. With no ref, or a ref no route carries, behaviour is
  unchanged.
- **Test:** `::test_a_late_call_of_a_retired_route_is_metered_at_that_routes_rate`. Before
  the fix the keyword did not exist; the semantic before-state is the second assertion,
  where no ref gives `premium` for a `studio` call.

### D2-05 (P3): "Calls today" disagreed with today's bar

- **Where:** `crm/service.py::dashboard`.
- **Problem:** `calls_today` counted `started_at` in IST today. The chart files calls by
  `lens.CALL_AT` (connected, else placed). A dial that failed before ringing was in the bar
  and its "missed" link, but not in the tile.
- **Fix:** `calls_today` is now the chart's today bucket, one count. The redundant column
  was removed and the counts row is read by name.
- **Test:** `::test_calls_today_counts_what_todays_bar_counts` (1 vs 2 before).

### D2-06 (P3, auth): Google sign-in with a stale invitation created an account and then refused (Z5 P3)

- **Where:** `authn/self_serve_routes.py::google_complete`.
- **Problem:** `google.finish` ran first. With signup open it created the account and a
  session nobody received, then `accept_for_verified_address` raised `invitation_invalid`.
- **Fix:** an unusable invitation (`invited_address` is None) is refused before
  `google.finish`. `invitations._invalid` was made public as `invitation_unusable`.
- **Test:** `tests/self_serve_account_test.py::test_a_stale_invitation_is_refused_before_google_opens_an_account`.

## Proven not real

- **Z3-N2 (a non-terminal status overwriting another).** Every non-terminal writer runs
  through `ingest_engine_event` under one arq `job_id`:
  - `job_id_for(INGEST_JOB, engine, id, "reconcile")`, pipeline.py ~5944, ~6075 and ~6293.
  - arq will not start a second job with that id while one is queued or running, so two
    non-terminal reads of one call cannot interleave.
  - The webhook path is terminal-only (`call.completed`, `call.analysed`).
  - The terminal guard (`WHERE calls.status <> ALL(:terminal)`) covers terminal against
    non-terminal.
  - No change.

    signal worth the retry noise. FOUNDER DECISION below.
- **P3: analytics and the dashboard file calls differently.**
  - `analytics/service.py` buckets calls by `started_at` (`_CALLS_IN_RANGE`,
    `_TIMELINE_SQL`), as its module docstring states.

  - So a failed-before-ringing dial is in the dashboard's day but not in Performance's.
  - This is a definition choice across two screens, not a defect inside either. Unifying
    it changes a client-visible number on Performance, so it is reported.
