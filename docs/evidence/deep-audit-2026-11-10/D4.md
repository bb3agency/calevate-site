## Findings fixed

### D4-01 (P1, availability of the whole box): a small Word or Excel file parsed into gigabytes, in a worker with no memory ceiling

- **Where.** `apps/workers/document_text.py::_open_ooxml` (the only bomb pre-flight was the
  256 MB DECLARED TOTAL, `MAX_OOXML_EXPANDED_BYTES`) and `compose.prod.yml` `workers-bulk`
  (no `mem_limit`). Document reads run on `workers-bulk` (`core/queue.BULK_JOBS`:
  `ingest_kb_source`, `read_kb_upload`); the only `mem_limit` was on `workers`, whose comment
  still named document reads.
- **Measured in Docker** (`--memory 3g`, peak RSS of `read_document`, each case its own
  process; scripts `scratchpad/d4/d4_ooxml_read.py`, `d4-measure.sh`):

  | file | upload | declared XML | peak RSS |
  |---|---|---|---|
  | DOCX, body of empty `<w:p/>` | 98 kB | 64 MB | 1122 MB |
  | DOCX, body of empty `<w:p/>` | 382 kB | 250 MB | OOM-killed at 3 GB |
  | DOCX, one-letter paragraphs | 763 kB | 250 MB | OOM-killed at 3 GB |
  | XLSX, 250 MB shared-strings table | 641 kB | 250 MB | 1446 MB, 70 s |
  | DOCX, empty paragraphs | 49 kB | 32 MB | 582 MB |
  | DOCX, empty paragraphs | 25 kB | 16 MB | 322 MB |

  All of these pass the 256 MB total. The tree (or openpyxl's shared-strings list) costs
  ~17x the XML. On the 3.8 GB starter with no ceiling on `workers-bulk`, one member's upload
  hands the choice to the host OOM killer, whose pick can be Postgres.
- **Second defect, the reason nobody saw it:** `tests/starter_sizing_test.py` searched the
  text from `workers:` to `migrate:`, a span that includes `workers-bulk`, so it passed on
  the main worker's line alone. `docs/DEPLOYMENT.md` §2b still said "No compose service sets
  a `mem_limit`".
- **Fix (`9f81a0b6a`).**
  - `document_ingest.MAX_OOXML_PART_BYTES` (32 MB): `_open_ooxml` refuses any XML/rels part
    parsed WHOLE over it, from the central directory (no decompression). Worksheets are exempt,
    because openpyxl `read_only` streams them and a big price list must still read. A lying
    header buys nothing: CPython's `zipfile` stops a member at its declared size and the CRC
    then fails. The worst 32 MB body peaks at 582 MB. The 250 MB files above are now refused at
    34 MB RSS.
  - `workers-bulk` `mem_limit: ${WORKERS_BULK_MEM_LIMIT:-1024m}` (idle 186 MB plus the 582 MB
    worst parse). Both workers together are capped at 2.5 GB of the 3 GB that is left. The test
    now loads the YAML and checks each service by itself.
  - DEPLOYMENT §2b states the ceilings and the measurement.
- **Tests.** All three failed on the old code (`DocumentEmptyError` instead of a refusal;
  `AttributeError`; `KeyError: 'mem_limit'`):
  - `tests/document_text_test.py::test_a_small_docx_whose_body_would_parse_into_gigabytes_is_refused_before_the_parse`
  - `::test_a_worksheet_over_the_part_ceiling_still_reads_because_it_is_streamed`
  - `tests/starter_sizing_test.py::test_the_worker_has_a_memory_ceiling_inside_what_the_starter_can_spare`
- **Operator note.** `WORKERS_BULK_MEM_LIMIT` is a new optional variable. The default suits
  the starter. A PDF read's peak memory on `workers-bulk` is still UNMEASURED. If a real PDF
  is ever OOM-killed at 1024m, raise the variable; that does not mean the parse needs
  changing.

### D4-02 (P2, data rights): a link removed while the sweep was reading its page came back (Z8's UNVERIFIED item, proven)

- **Where.** `apps/workers/kb_ingest.py::_recheck_link` and
  `apps/api/kb/uploads.py::remove_upload`.
- **Failure.** The sweep reads its due rows first (`_DUE_LINKS_SQL`, `_due_link_sources`).
  It then fetches each page over the network outside any transaction. Across a tick, the gap
  between reading the row and filing the change is the fetch time of every link before it.
  If the owner removes the link in that window, `remove_upload` deletes the row. The re-read
  then runs `insert_source_version` under the removed name. The changed page comes back as a
  new knowledge item, waiting for review. The linker lookup reads through the deleted row,
  so the item is not auto-approved, but an approval puts the removed page back on the agent.
- **Fix (`1795895f5`).** `_recheck_link` takes `SELECT … FROM kb_uploads … FOR UPDATE` on
  the checked row before it files anything, and stops if the row is gone. `remove_upload`
  takes the same row lock first. So a removal either finished before the re-read (no row) or
  waits for the re-read to commit.
- **Test.** `tests/kb_auto_publish_test.py::test_a_link_removed_while_its_page_is_being_read_does_not_come_back`.
  The owner removes the link from inside the fetch. On the old code it failed with
  `assert True is False`: the re-read reported a change and filed a version.
- **Residual: still a founder question, as Z8 said.** If a re-read COMMITTED a new version
  before the removal, that version stays. It is listed as its own row, so the owner can see
  it and remove it.

## FOUNDER DECISION

### FD-1: Pip's hourly memory distillation is charged to the client's AI allowance, with no allowance check

- **Facts at source.**
  - `apps/workers/copilot_memory.py::_distil_group` records `ASSIST_FEATURE_COPILOT_MEMORY`
    (`copilot_memory_distillation`) through `record_ai_assist_usage`.
  - That feature is not in `billing/models.ABSORBED_ASSIST_FEATURES`, so it counts against
    the monthly allowance.
  - `distil_copilot_memories` checks only `platform_brake_tripped`. It never calls
    `require_ai_assist`.
  - So work nobody asked for keeps adding to an account's usage after the account reaches its
    ceiling. Fleet-wide it is bounded by `MAX_GROUPS_PER_TICK` per hour; per account it is
    not bounded.
- **Option A: absorb it (we pay).**
  - Add `ASSIST_FEATURE_COPILOT_MEMORY` to `ABSORBED_ASSIST_FEATURES` in
    `apps/api/billing/models.py`. That is a one-line change.
  - The row stays in `usage_events` at its model cost (hard rule 7). It leaves the client's
    allowance and the fair-use cap.
  - Test: `read_ai_quota` excludes a `copilot_memory_distillation` row.
- **Option B: gate it (the client pays, but only within the allowance).**
  - In the per-tenant loop of `distil_copilot_memories`, before reading groups, use the shape
    `business_copy._may_spend` already uses: `try: await require_ai_assist(session,
    tenant_id=tenant_id) except ProblemError: continue`.
  - Episodes keep `distilled_at IS NULL` and are distilled after the IST month rolls over or
    the allowance is raised.
  - Test: an account at its ceiling gets no model call and no usage row, and its episodes
    stay pending.
- I built neither, because the brief says not to decide.
