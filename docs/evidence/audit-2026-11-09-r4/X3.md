# Backend audit round 4, lane X3: workers, jobs and reliability (9 Nov 2026)

Base `bc78e5ea4`. Tests: `tests/audit_2026_11_09_x3_test.py`. No migration.

## FIXED

### X3-01 (P1) Signed-webhook retries, "Send again" and the LeadSquared echo check read a body the consumer had already blanked

- **Where:** `apps/api/reliability/service.py::mark_outbox_consumed` set `payload = '{}'` for
  every job on success (L5-03, 5 Nov). Three readers still need the body of a
  `deliver_outbound_webhook` message after its first run succeeds:
  - `integrations/service.claim_due_retries` and `outbound_webhooks.retry_outbound_deliveries`;
  - `integrations/service.resend_delivery` ("Send again");
  - `ingest/routes._sent_to_leadsquared`.
- **Failure, retries:** a 5xx or timeout on a signed webhook records `retrying` and *returns*.
  `consume_outbox_once` then marks the message consumed and blanks the body. When the retry
  falls due, the sweep enqueues `{"attempt": 2}` (`{}` is a dict, so it is not caught as
  "body not held"). `deliver_outbound_webhook` raises `KeyError('tenant_id')`, which is
  terminal, so nothing is recorded. The 15-minute claim lease then lapses and the same row
  is claimed and crashed again, for ever. In short, no signed webhook ever got its second
  attempt.
- **Failure, "Send again":** this queued the same empty body.
- **Failure, LeadSquared echo:** once our write to LeadSquared had succeeded, the echo check
  joined on `payload->>'endpoint_id'` and `payload->'data'->>'lead_id'` of a blanked row.
  LeadSquared's lead-create webhook for our own write was then ingested as a new lead (a
  second call to the person). The existing test `lead_source_portals_test::
  test_the_echo_is_recognised_after_our_write_has_left_the_queue[delivered]` set
  `consumed_at` by hand without the scrub, so it never saw this.
- **Fix:**
  - `KEEP_PAYLOAD_AFTER_RUN_JOBS = {"deliver_outbound_webhook"}`; `mark_outbox_consumed` keeps
    the payload for these jobs. The body is still pruned at 90 days and destroyed by erasure
    (`retention._erase_outbox_messages`), which is the window "Send again" already promises.
  - A row already blanked by the old code (`{}`) now counts as not held. The retry sweep ends
    it `failed` / `delivery_body_not_held` instead of looping, and "Send again" and the
    delivery list's can-resend flag refuse it (`integrations/service.py`,
    `integrations/routes.py`).
- **Tests:**
  - `test_a_retry_after_the_registered_job_ran_carries_the_whole_body`
  - `test_a_body_blanked_before_the_fix_ends_the_retry_instead_of_looping`
  - `test_leadsquared_echo_is_recognised_after_the_consumer_recorded_the_delivery`
  - `test_other_jobs_still_forget_their_payload_on_success`
  - `test_the_kept_job_is_the_crm_delivery_job`

  The first three fail on the old code: retries were enqueued without `delivery_id`, and the
  echo was accepted as a lead.
- **Production:** deliveries stuck `retrying` with a blanked body cannot be recovered; after
  this deploy they end `failed` with "We no longer hold what was sent". Query to size it:
  `SELECT count(*) FROM webhook_deliveries d JOIN outbox_messages m ON m.id = d.outbox_message_id WHERE d.status = 'retrying' AND m.payload = '{}'::jsonb;`

### X3-02 (P2) A KYC decision email was swallowed by the previous submission's spent key

- **Where:** `compliance/kyc_review.decide_kyc_review` keys `enqueue_outbox_once` on
  `kyc-decision:{tenant}:{submitted_at}`. However, `compliance/kyc.record_kyc` (the signatory
  run's writer, `kyc_verification.apply_outcome` with status `submitted`) kept
  `COALESCE(old submitted_at)`.
- **Failure:** a company or LLP is rejected, then verifies its signatory through the
  aggregator. The record goes back to review with the old instant, and the reviewer's second
  decision finds the key spent. The client is never emailed that it was approved or rejected,
  while outbound stays gated on KYC.
- **Fix:** `record_kyc` stamps `submitted_at = now()` when a record moves into `submitted`
  from anything other than review. This is the rule `submit_for_manual_review` already
  follows.
- **Test:** `test_a_signatory_run_after_a_rejection_is_told_its_own_decision`. It fails on the
  old code with one notice instead of two.

## Verified sound (read at source)

- **Every `enqueue_outbox_once` key (41 sites) checked for a later legitimate run colliding
  with a spent key:**
  - `hot-facts` daily: only the sweep uses it; changes use a plain enqueue.
  - `business-copy` (fixed earlier today).
  - `agent-move` (hourly sweep passes a tick).
  - `rate-card-notice` (a re-record at the same instant is refused, because cancelled cards
    still count in `_CARD_EXISTS`).
  - `credit_lapse_notice`, `trial_minutes_used`, `trial_started`, `follow-up-drive` (the
    minute tick re-drives by token anyway), `follow-up-call-ended`, `after_call_actions`,
    `save-number`, `call-language`, `inbound-cutover`, `team-alert`, `hot-lead*`,
    `campaign-escalation`, `retire-engine-agent`, secret rotation `:{version}`,
    `tenant_erasure_redrive:{window}`, `dispute-outcome:{id}:{phase}:{status}`,
    `kyc-decision` (X3-02).
- **New `dial_lost` sweep (`pipeline.reconcile_outstanding_calls`, c75381c7e):**
  - CAS on the placeholder and `queued`, and a contact still `dialing` is excluded, so there
    is no double dial.
  - Both workspaces are asked.
  - Probes count against the budget, and failures alarm.
  - A closed `failed` row releases follow-up runs (`settle_orphans`) and callbacks
    (`callbacks.service` settle reads `failed`).
- **Locks and leases:**
  - Every advisory lock is `pg_advisory_xact_lock`; no session lock can leak.
  - The Redis leases in campaign_dispatch, engine_workspace_events and core_labels are
    released in `finally` or by TTL.
- **Loops:**
  - `resumed_walk` leaves the cursor on the last tenant it finished.
  - arq `Retry` is bounded by `max_tries`.
  - The `while True` loops in workers (copilot_plans, first_run, retention pages) settle or
    advance each pass.

## NOT FIXED

- **X3-03 (P3), a description reverted to an earlier one is never re-drafted:**
  - Where: `profile-wording:{tenant}:{known}` (`tenancy/profile_wording`),
    `starter-steps:{tenant}:{known}` (`agents/starter_plans`) and teach-question drafts
    `{job}:{tenant}:{key}:{fingerprint}` (`teach/questions._queue_draft`).
  - Failure: when the description goes A, then B, then back to A, the A key is spent, so the
    wording, steps or draft written for B stays. This also happens after one refused or
    crashed run for A ("no retry" is documented in each worker).
  - Impact: the cost is display only. Neutral or slightly stale labels, platform steps, or a
    question with no draft offered.
  - Why not fixed: changing the key needs a decision on how many paid re-asks per
    description are acceptable.
- **X3-04 (P3), "once ever" keys expire with the outbox prune:** the 90-day
  `retention.prune_reliability_tables` deletes published rows, and their dedupe keys with
  them. For example, `campaign-escalation:{contact}` could message a contact again if the
  same contact is re-exhausted more than 90 days later. This is UNVERIFIED as reachable in
  practice.
- **X3-05 (P3), the found branch can repeat for ever on an unadoptable dial:** if the engine
  holds the call and the ingest cannot adopt the placeholder (a vendor row already exists
  under the handle, `_ADOPT_UNCONFIRMED_DIAL_SQL` NOT EXISTS), the placeholder stays `queued`.
  It is re-probed every 2 h with no age limit, and each probe re-queues an ingest.
  UNVERIFIED as reachable: every row-creating source (Get Call, List Calls, `call.completed`
  for API-placed calls) carries `reference` per the 2026-10-28 webhooks.md:354 mirror.
- **X3-06 (P3), misleading remediation on the rate-card conflict:** the "rate card already
  scheduled" conflict (`ops/config_routes`) tells the operator to "Withdraw the scheduled card
  first ... then record this one". A withdrawn instant is still refused, so only "choose a
  different instant" works. This is admin wording only.
