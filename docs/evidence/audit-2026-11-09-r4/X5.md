# Lane X5: API contract, error paths and the ThinnestAI engine adapter (9 Nov 2026, round 4)

Base `bc78e5ea4`. No migration. No wire change (no route, schema or OpenAPI shape moved).

## Fixed

### X5-01 (P1, call-breaking): a dial the adapter refused before `POST /calls` read as "the phone may have rung"

- **Where.** `apps/api/engine/thinnest.py::_outbound_opening` and `_dial_variables` raise
  `carrier_dial_precondition_failed` before any dial request is sent: the agent read failed,
  the greeting is missing, or the call's variables do not fit. `apps/api/agents/service.py::
  DIAL_NOT_PLACED_CODES` no longer listed that code. Commit `7de7bcc3b` (D-763, 13 Oct 2026)
  removed it as the owned runtime's (`engine/pipecat._dial_precondition_failed`), but the
  ThinnestAI adapter raises the same code. The comment above the constant in `thinnest.py`
  still said the set "already treats" it as not placed.
- **Failure.** `dial_was_not_placed` answered False, so `dispatch_call` raised
  `DialUnconfirmedError`. In a campaign that runs `_settle_unconfirmed_dial`: the contact is
  finished for good and the client gets an escalation. The CRM buttons warn that calling
  again could ring the person twice. The intent row stays `queued` under `local:<id>` and
  holds an outbound line until `reconcile_outstanding_calls` closes it as `dial_lost`, which
  happens no sooner than 10 minutes later. Every dial reads `GET /agents/{id}` first, so a
  single per-minute throttle (`rate_limit_resources`, errors.md "Limits") or a 5xx during a
  campaign tick ended every contact the tick reached, and none of those people had been
  called.
- **Second defect on the same read.** Any failure, a throttle included, was worded "the
  published agent is missing / Publish the agent again", which sent the owner to republish
  for a vendor hiccup. Because a throttle came back as a precondition failure, the dial
  hold-off (`start_dial_backoff`) also never started.
- **Third.** An opening that the publish accepted (≤ 200 characters) can grow past
  `purpose`'s 300 (thinnest-findings/mirror/snapshots/2026-10-29/pages/api-reference/calls/
  place-call.md:7, "300 characters or fewer") once `{{lead_name}}` is filled in. It raised
  the publish's `engine_greeting_too_long`, which is also not in the set, so it was also
  treated as unconfirmed.
- **Fix (commit `06e008b73`).** `DIAL_PRECONDITION_FAILED` moved to
  `engine/capabilities.py`, because business modules may not import the adapter (import-linter
  "engine isolation"), and was added to `DIAL_NOT_PLACED_CODES`. In `_outbound_opening`:
  - `EngineRateLimitedError` is re-raised as itself, so it stays `engine_rate_limited`, which
    is already not-placed, and it starts the hold-off;
  - a 404 about the agent keeps "published agent is missing";
  - any other read failure says the platform did not answer, nobody was called, try again;
  - an opening over 300 characters after the fill raises the precondition code with its own
    sentence.
- **Tests.** `tests/audit_2026_11_09_x5_test.py`:
  - `test_a_dial_whose_opening_could_not_be_read_is_proven_not_placed`
  - `test_a_platform_that_did_not_answer_is_not_called_a_missing_agent`
  - `test_a_throttled_agent_read_stays_a_throttle`
  - `test_an_opening_too_long_with_this_calls_name_is_refused_unplaced`
  - `test_a_campaign_contact_whose_dial_was_never_built_keeps_its_place`: through
    `campaign_dispatch._dispatch_for_campaign`, the contact goes back to `pending` with no
    attempt spent and the intent row ends `failed`.

  All five fail on the pre-fix sources (run with `HEAD~1`'s three source files) and pass with
  the fix.

## Verified sound (read at source, not changed)

- **`vendor_http._vendor_response`.**
  - Every client has a timeout: `REQUEST_TIMEOUT_S`, test chat 30 s, knowledge links 60 s,
    status 2 s.
  - Only 429 is retried. That is safe on `POST /calls` with the idempotency key
    (place-call.md:299-310), and on other POSTs because the request was refused.
  - A 3xx is refused, not followed.
  - A 2xx with a non-JSON body is refused.
  - A body over the cap is refused, not truncated.
  - A 404 scoped to the workspace (`workspace_not_found`) is never read as the object being
    absent.
- **Dial refusal mapping (`_dial_refusal`).** It was checked against
  snapshots/2026-10-29/pages/api-reference/errors.md "Placing a call":
  - every documented not-placed code is in `_DIAL_NOT_PLACED_CODES`;
  - `idempotency_in_progress` stays unconfirmed;
  - `carrier_unavailable` 502 is treated as setup.
- **`find_placed_call` and `placed_reference` (c75381c7e).**
  - The `reference` filter is exact (list-calls.md:484-493).
  - `items` is required.
  - A row naming another reference is refused.
  - Our dials send `ifOutsideHours: refuse` and no `scheduledAt`, so none is booked.
- **`_walk` (1cbe8d949).** Every paged list it walks declares `items` and `nextCursor`
  required in the 2026-10-29 snapshot: calls, agents, knowledge, usage/list-call-log, models.
- **`end_call` (1cbe8d949).** Only a 404 about the object proceeds to DELETE.
- **voice-runtime signed intake.**
  - v2 HMAC over `<delivered-at>.<body>`.
  - A ±5 min window on `x-thinnest-delivered-at`.
  - The event-id header must match the body `id`.
  - Signature and agent/workspace mismatch are both checked.
  - The body is sealed before it is queued.
  - One deadlined transaction for claim, forensic row and enqueue.
  - The Redis fast path is written only after commit.
  - A body read bounded in size and time.

  `call.completed` and `call.analysed` key on the same call id: `id` equals `callRef` for an
  inbound call (get-call.md:845-855).
- **Caller lookup (`/v1/worker/engine-lookups`).** Signed, budgets inside the vendor's 2 s,
  a repeat answered from the first answer, and every failure answers 200 with no variables.
- **API error envelope.** Every handler answers problem+json (`core/errors.
  install_error_handlers`). Lane T4 (8 Nov) fuzzed all routes; the new route since then
  (`POST /v1/auth/client/mobile-number`, D-976) bounds its input and refuses an unreadable
  number with a field error.

## Not fixed

- **X5-N1 (P2, UNVERIFIED in a live incident): placeholder dials are outside both recalls.**
  `queued_dial_scan` (alembic `b7e4c0a63f29`) and the DNC recall's SQL both skip
  `engine_call_id LIKE 'local:%'`. A dial is a placeholder from its intent row until
  `_confirm_dial`, which includes the pre-dial caller lookup and the `POST /calls` round
  trip, and it stays one for good when the answer is lost. So:
  - the big red switch thrown in that window does not reach it, and `dial_recall` scans once;
  - a DNC addition in that window does not stop it either.

  The campaign tick re-reads the halt per contact (`campaign_dispatch`, `force_refresh=True`),
  which narrows the window but does not close it. The halt is best-effort by decision (D-428).
  Closing the window needs either a post-dial halt/DNC check in `dispatch_call` that ends the
  call, or a recall pass that resolves placeholders through `find_placed_call`. Both change
  the recall design, so this is left for the coordinator to decide rather than built here.
- **X5-N2 (P3): three single-page reads take a missing `items` as an empty list.** This is
  V2-01's defect class, not yet fixed in these:
  - `ThinnestCustomers.find` (`engine/thinnest_customers.py:181`);
  - `ThinnestActions.has_live_call` (`engine/thinnest_actions.py:522`);
  - `ThinnestNumbers.cities` and `.search` (`engine/thinnest_numbers.py:357, :376`).

  Each is backstopped, so nothing wrong is written:
  - provisioning's create is idempotent and answers 409 on a taken reference;
  - deleting an agent on a live call is refused with `409 agent_on_live_call` and retried;
  - the number screens show "none available".

  Left alone under the brief's "no change that changes nothing".
