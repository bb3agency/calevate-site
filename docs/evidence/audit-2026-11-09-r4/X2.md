## Findings

### X2-01 (P2): a co-owner's WhatsApp alerts silently stop once an earlier owner has a number

- Where: `apps/workers/whatsapp.py::resolve_destination` and
  `apps/api/compliance/whatsapp_optin_routes.py::_owner_of` (before the fix both ran
  `... WHERE m.role = 'owner' AND u.phone IS NOT NULL ORDER BY m.created_at LIMIT 1`).
- What went wrong: alerts went to the earliest owner who had a number, whether or not they
  had agreed. Opt-ins are keyed on (tenant, person, number), and the client route records an
  opt-in for the person who presses the switch. So when an account had two owners and the
  later one opted in, the alert job asked the earlier owner's ledger, found nothing, and
  refused every alert as `recipient_not_opted_in`. Meanwhile `GET /v1/compliance/whatsapp-alerts`
  showed the co-owner `messageable: true`. The same wrong subject was used by
  the account-closure and campaign-archive notices (both go through `resolve_destination`), and
  by the operator's read and record surface.
- Why it matters now: before D-976 (`bca544e16`) only an invitation wrote `users.phone`, so a
  self-signed-up founding owner had no number and was skipped. D-976 lets that owner add one
  on Your account, and the automatic top-up refusal sends them there. Adding a number is enough
  to shadow the co-owner's opt-in, with nothing on screen to show it.
- Fix: `compliance/whatsapp_optin.alert_subject` is now the one answer to "which owner is
  alerted". It picks the earliest active owner who has agreed, at the number they agreed on.
  If no owner has agreed, it falls back to the earliest owner with a number, and that owner's
  state still refuses. The worker and the operator surface both call it.
- Test: `tests/whatsapp_optin_test.py::test_an_owner_who_opted_in_is_alerted_when_an_earlier_owner_has_a_number`.
  It failed before the fix with `assert '+919000000055' == '+919000000056'` and passes after.

### X2-02 (test gap, closed): admin routes with a neighbour's child id in the path

`adversarial_pass_test` sweeps client-space `{id}` routes with a neighbour's real ids.
`absent_tenant_answer_test` sweeps `/v1/admin/tenants/{tenant_id}/…` routes with a tenant that
does not exist. Neither tested a real tenant B in the path with a real child id belonging to
tenant A (for example `/v1/admin/tenants/{B}/agents/{A's agent}/publish`). That is one paste
away for an operator. A handler that read the child outside `tenant_session(tenant_id)` would
act on A's object while the audit row, the step-up string and the engine workspace named B.

- New file: `tests/admin_neighbour_child_id_test.py`. It is built from the live route table:
  every `/v1/admin/...` route whose path holds `tenant_id` plus an object id, which today is
  50 routes, including the engine-workspace and number routes.
- How it drives each route: it uses the body from `absent_tenant_answer_test.BODIES`. It
  passes the step-up gate by sending back the `X-Confirm-Action` the refusal names. It expects
  404 `not_found` and no audit row on A.
- Result: every route answered 404. No defect found.
- Non-vacuity, checked with a scratch run that is not committed: with A's own tenant in the
  path, 39 of the 50 routes reach the object (200/201/409/422 business answers). The other
  11 answer 404 even for the right tenant, because the seeded id is of another kind with the
  same parameter name (`request_id`, `source_id` and similar). For those 11 the sweep proves
  less.

## Verified sound (read at source or run)

- Guard suite green, 239 tests: rls_sweep, adversarial_pass, rbac_registry, realm_boundary,
  cross_tenant_reference, authz_audit, rls, ambient_tenant_session, rls_bypass_objects_guard,
  rls_exempt_untenanted_write, impersonation_writes, impersonation_reads, authn_stepup,
  member_invitations, members, authn_rls, authn_flow_rls.
- No new tenant table since round 2 (`ad8e9d40c`): the four migrations since only add
  columns. No `SECURITY DEFINER` function exists in `alembic/versions`.
- `POST /v1/auth/client/mobile-number` (`bca544e16`):
  - reads only the client cookie, so view-as gets 401;
  - writes in one statement under a row lock;
  - audits the kind of change, never the number;
  - the number is global per person, which is the intended behaviour for someone who
    belongs to more than one account.
- V1-03 invitation accept lock (`909dbe75a`): the lock is taken first in the burning tenant
  transaction and the invitation is re-read under it. The Google path takes the same lock.
- D-955 reclaim only applies to an unproved address.
- Step-up action codes:
  - client action strings carry the `X-Org-Slug` the principal was resolved from, so a code
    proved in one account cannot be spent in another;
  - a view-as session has no client cookie and is refused, except with local dev tokens.
- Multi-account people:
  - the membership is re-read on every request;
  - `org_required` is returned when more than one account matches and no slug was sent;
  - queued Pip work re-reads `acting_member_role`, which covers removal and deactivation.
- Member role change: a CAS on `expected_role`, so `expected_role: owner` cannot skip the
  owner-promotion code.
- Members, invitations and Pip consent are withheld from view-as. Number purchase needs a
  client action code.
- `users` has no RLS. Every client-path read of it is joined through `memberships`, uses the
  caller's own id, or is admin-only.
- The secb open item (assign before `assert_visible`) is fixed:
  `campaigns/number_catalog.assign_number_to_agent` now calls `assert_visible` first.
