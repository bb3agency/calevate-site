## Fixed

### X4-01 (P1, compliance): a WhatsApp message id kept the recipient's number where no erasure reaches

- **Where.** `apps/api/crm/swipe.py::record_whatsapp_on_timeline` and `_NOT_DELIVERED_SQL`
  (added by 44f0163ae, 9 Nov) wrote Meta's `wamid.` message id into `lead_events.payload`.
  `apps/api/whatsapp/webhooks.py::_from_change` put the same id into the `send_failed`
  event that is queued as an outbox job.
- **Why it is personal data.** A `wamid.` id is base64 of a record that holds the
  recipient's number in clear. Meta's own example status id
  `wamid.HBgLMTY1MDM4Nzk0MzkVAgARGBI3...` decodes to the digits `16503879439`
  (developers.facebook.com/docs/whatsapp/cloud-api/webhooks/payload-examples, read 9 Nov
  2026). The voice platform's example id
  (`thinnest-findings/mirror/snapshots/2026-10-13/pages/api-reference/messages/send-message.md:455`)
  decodes to `919876543210`.
- **Failure scenario.** A client sends a lead a WhatsApp follow-up. Later that person asks
  for DPDP erasure. `execute_deletion_request` empties the lead, but `lead_events` is in
  `ERASURE_EXEMPT` (`scripts/check_erasure_coverage.py`). The exemption rests on the claim
  that no producer writes a phone number. The timeline row therefore keeps the person's
  number, base64-encoded, and the §12 certificate says it is gone. Tenant erasure never
  deletes leads, so the same holds after an account is erased. The queued `send_failed`
  job holds no `tenant_id`, so `_OUTBOX_SUBJECT_SQL` cannot match it, and its digit-run
  match would not see a base64 number anyway.
- **Fix.** `whatsapp/webhooks.message_ref` returns the SHA-256 hex digest of the id. The
  timeline stores `message_ref` and never the id. The webhook emits `message_ref` for a
  failed delivery. `record_whatsapp_not_delivered(ref=...)` matches on the digest, so a
  late failure report still reaches its send. The id's random half means the digest cannot
  be reversed by trying every number.
- **Migration (needed: production may hold rows written since 44f0163ae).**
  `alembic/versions/d9a4e7c2b1f6_lead_timeline_keeps_no_whatsapp_message_id.py`,
  **down_revision `c3f8a1d6e4b9`** (the single head after bc78e5ea4). It rewrites existing
  `message_id` values to `message_ref` with the same digest Postgres computes, inside a
  NO FORCE / FORCE RLS bracket. On downgrade the digest goes back under `message_id`; the
  ids themselves cannot be recovered. **The coordinator re-points heads at merge.**
- **Tests.** `tests/audit_2026_11_09_x4_test.py`:
  - `test_a_whatsapp_message_id_carries_the_recipients_number` proves the premise.
  - `test_a_leads_timeline_keeps_no_message_id_and_still_finds_the_failure`.
  - `test_the_migration_digests_a_stored_id_as_the_code_does`.
  - `test_a_failed_delivery_report_carries_no_message_id_into_the_queue`.

  The existing `tests/audit_2026_11_08_v5_test.py` now passes `ref=`.

## Verified sound (read at source, guards run)

All three were run on the lane DB at the base.

- **Dial sites.** Every `dispatch_call` caller asks `check_dispatch` first: `lead_dial`
  (call now and call back), `one_call` (a new person is gated before any lead is made), the
  callbacks worker (fresh halt read and per-callback gate, and follow-up steps ride it), the
  campaign tick, `trial_calls` and the ingest new-lead dial. Pip's `call_place` goes through
  `place_one_call`. The forwarding test call is a documented, narrower gate. WhatsApp sends
  ask `check_dispatch(places_call=False)`.
- **Gate order.** Halt (fresh unless the caller read it), drain, stopped account, agent and
  disclosure, truthful-answer drift, account blockers, trial line cap, calling hours (IST,
  owner's attested number excepted), person level (India-only, anonymised placeholder,
  live tenant and global DNC read, consent ledger), and the a2p declaration.
- **DNC.** `add_to_dnc` and `add_numbers` recall queued dials, push only to the client's
  own workspace and cancel call-backs. `remove_entry` and `restore_optout` queue the
  workspace removal. The workspace creation backfills existing entries
  (`workers/engine_workspaces.py:185`). The engine's `contact.opted_out` files on the
  hearing tenant and refuses the business's own number.
- **Exports.** Calls and leads CSV and Pip's prepared export are `calls:read_raw`, need an
  emailed code and are audited in the handler. The subject export is `calls:read_raw` and
  audited. Pip's raw call read needs `calls:read_raw` and consent, and is audited.
- **Logs and alerts.** `REDACT_KEYS` with message, extra and exception scrubbing. Alert
  `detail` is redacted before the console row and the mail.

## Not fixed

- **X4-N1 (P3, UNVERIFIED).** A dial whose vendor answer was lost keeps a `local:` id.
  Both `queued_dial_scan` and `_recall_erased` skip `local:` rows
  (`alembic/versions/b7e4c0a63f29_*`:66, `workers/dnc_recall.py:203`). So a DNC addition or
  an erasure in that window cannot recall the dial if ThinnestAI is still holding it
  queued. Since c75381c7e the outstanding-calls sweep can find such a call by `reference`,
  which would make the recall possible. Not changed because I did not establish how long
  ThinnestAI keeps a dial queued, and it needs a lost answer and a suppression in the same
  window.
- **X4-N2 (P3).** A Pip `call_place` approval for a number not yet on file is logged with
  `object_id = 'new:<attempt>'`. `_COPILOT_ACTION_ERASE_SQL` matches by lead or call id, so
  a subject erasure inside the 24 h approval window leaves the raw number in
  `pending_args`. Approving it then rings the erased person. It needs a background routine
  to propose a call to a typed number within a day of an erasure. The name in `summary`
  sits under the published "assistant / by name" limitation.
- **Environment.** Docker Desktop's engine returned HTTP 500 for about 30 minutes
  mid-lane, and the server then reported 29.8.2, not the 29.7.2 in the machine
  rulebook. I did not touch it.
