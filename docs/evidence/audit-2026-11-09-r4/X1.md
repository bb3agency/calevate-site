## Fixed

### X1-01 (P2): a lost dial the engine later turns out to hold kept reading "nobody was rung"

`apps/workers/pipeline.py` `_ADOPT_UNCONFIRMED_DIAL_SQL` (and the upsert's
`not_placed_reason = COALESCE(EXCLUDED…, calls…)` / terminal guard below it).

The lost-dial sweep (c75381c7e) closes a `local:` intent row `failed` / `dial_lost` when the
engine's search by reference comes back empty, and keeps the placeholder id so "a call the
engine lists only later is still adopted". Adoption changed only `engine_call_id`, so:

- a call that then **completed** became `status = completed` with `not_placed_reason =
  dial_lost` (the COALESCE keeps the old value). It was metered and charged like any call
  (`_meter` does not read `not_placed_reason`), while the call page said "This call did not
  go through, so nobody was rung." (`crm/service.NOT_PLACED_WORDS`), Pip's diagnostics said
  it never went through, and `paid_test_calls.PLACED_TODAY_SQL` did not count it against the
  paid daily test-call cap;
- a call that rang and was **not answered** (`no_answer`, `busy`, …) could not replace
  `failed` (the upsert's terminal guard lets only `completed` through), so it stayed
  `dial_lost` although the person's phone rang.

Fix: adopting a row the sweep had closed as `dial_lost` reopens it (`status = 'queued'`,
`not_placed_reason = NULL`) in the same statement, so the upsert that follows in the same
transaction writes the call's real status. Rows with any other reason are untouched.

Test: `test_a_lost_dial_the_engine_later_shows_was_placed_reads_as_the_call_it_was[completed|no_answer]`.

### X1-02 (P3): a trial's daily test-call cap counted dials that rang nobody

`apps/api/billing/trials.py` `_TRIAL_CALLS_SQL` (read by `compliance/trial_access.read_trial_access`
→ `TrialAccess.blocker`, the `trial_daily_cap` refusal).

It counted every `trial_call` row of the IST day, including rows closed without ringing
anyone: `lines_full` (our dial path refused for full call lines), `dial_lost`, and the
engine's `from_number_withdrawn` / `unstated`. A trial owner could be refused "today's test
calls are used up" after calls that never rang. The paid twin, `PLACED_TODAY_SQL`, already
excludes them (`not_placed_reason IS NULL`); the trial query now does the same.

Test: `test_a_trial_dial_that_rang_nobody_does_not_use_up_a_daily_test_call`.

### X1-03 (P1): an auto-recharge could debit the client twice after a late authorisation

`apps/api/billing/auto_recharge.py` `settle_charge` (failure branch) and `expire_unanswered`.

Razorpay (LLM docs read 9 Nov 2026): a payment with no bank answer in 10 minutes is "marked
as Failed due to timeout", then Razorpay "polls the bank at various intervals for 3 days,
from the payment creation day" and marks it Authorized on success
(`payments/payments/late-authorisation.md`); "All payments `authorized` within 3 days from
the time of creation are auto-captured", the default (`payments/payments/capture-settings.md`);
captured payments are never auto-refunded (auto-refunds page, coordinator-relayed). Whether a
LATE-authorised payment is auto-captured is an inference from "auto-capture all", treated as
possible.

Two paths freed the one-pending slot (`ux_auto_recharge_charges_one_pending`) while the
first debit could still take the money, so the next five-minute sweep started a second:
- a `payment.failed` webhook failed the charge at once (`settle_charge(captured=False)` →
  `_fail_charge`);
- `expire_unanswered` failed every pending charge older than 3 days by age alone,
  including an unconfirmed one (`payment_provider_unreachable` etc.) whose payment was
  never read.
A failed charge also left `_month_spent`, so the monthly cap did not hold it.

Fix:
- `payment.failed` now only notes the code on the pending row.
- `expire_unanswered` reads the order's payments from Razorpay (new
  `RazorpayApi.order_payments`, `GET /v1/orders/:id/payments`, `api/orders/fetch-payments.md`;
  statuses created/authorized/captured/refunded/failed, also `api/payments/fetch-with-id.md`)
  and decides by `charge_verdict`:
  - any captured/refunded → credited through `payment_events.apply_captured` (the
    reconciliation's path, idempotent on the payment id) and the charge closed captured,
    so it counts against the month's cap;
  - any created/authorized, or a failed one younger than `LATE_AUTHORISATION_WINDOW`
    (3 days from the payment's creation) → stays pending, no new charge;
  - otherwise (all failed past the window, or no payment at all) → failed, with the
    webhook's code, and the client is told then.
- An unreadable provider leaves the charge pending. A capture that `apply_captured` refuses
  (amount or tenant mismatch) stays pending and pages `auto_recharge_capture_unplaced`
  (alarm index, severity and guide rows added).

Trade-off, stated: a declined debit is now told to the client and counted towards the
auto-off limit up to three days later, and no second recharge starts in between.

Tests: `tests/audit_2026_11_09_x1_recharge_test.py` (7, all failed on the old code). Updated
because the behaviour changed: `auto_recharge_flow_test` (a failed webhook only notes its
code; the expiry test reads a fake with no payments), `payment_operations_test`
(`test_a_failed_auto_recharge_debit_keeps_its_charge_pending_with_the_code`), and the e2e
`FakeApi.order_payments`.

  hold/release with lapsed credit: balance and lots stay equal in every path traced.
