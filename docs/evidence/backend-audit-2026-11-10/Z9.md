## Fixed

### Z9-01 (P1, compliance): a DPDP erasure whose one job failed stayed open for good

- **Where.** `apps/api/compliance/deletion.py::request_erasure` (dedupe branch) and
  `apps/workers/dispatcher.py::report_overdue_erasures`.
- **Failure scenario.** `execute_deletion_request` is queued once, with the request, runs in
  one transaction and raises no `arq.Retry`. A run that raises (a database error, a vendor
  call, `job_timeout`) is finished by arq on its first attempt (arq 0.28 retries only
  `Retry`/`RetryJob`/`CancelledError`, as `dispatcher.py` already records). The request
  then stays `completed_at IS NULL`. The client filing the erasure again dedupes onto the
  open request and nothing is queued. The hourly walk only paged
  `erasure_requests_overdue`, whose runbook row said "execute it by hand from the ops
  screen", and no such screen or script exists. The person's data is kept indefinitely
  after they asked for erasure. Tenant erasure already had the fix for the same shape
  (`tenant_erasure._redrive_if_stalled`); subject erasure did not.
- **Fix (b4d404161, f28e2abd8).** `deletion.redrive_stalled_erasure` queues the job again
  via `enqueue_outbox_once`, keyed `deletion_redrive:{id}:{hour window}`, for a request
  open longer than `DELETION_REDRIVE_AFTER` (1 h, the tenant rule). It is called from the
  re-filing dedupe branch and, through `redrive_stalled_erasures`, from the hourly
  overdue walk in the tenant session it already opens. The alert now says how many jobs
  were queued again. `execute_deletion_request` reads its request `FOR UPDATE`, so a
  re-driven copy that meets a late original waits and returns `already_completed`. Before,
  it read the row open, erased again and overwrote the certificate. The alarm index row
  and two stale comments ("cannot self-heal") are corrected.
- **Tests** (`tests/audit_2026_11_10_z9_test.py`; all three failed before the fix):
  - `test_refiling_an_erasure_whose_job_died_queues_it_again`
  - `test_the_hourly_overdue_walk_queues_a_stalled_erasure_again`
  - `test_a_redriven_copy_meeting_the_original_runs_once`
  - `test_refiling_a_fresh_request_queues_nothing_more` (healthy path, passes both ways)

### Z9-02 (P2, compliance): the subject access export withheld all but one CRM record

- **Where.** `apps/api/compliance/export.py::build_subject_export`, `SubjectExportOut`.
- **Failure scenario.** `leads` is unique per (tenant, number, agent). A business with an
  inbound receptionist and an outbound agent therefore holds two records for one person.
  The export carried the newest record as `lead` and reported the others only through
  `counts.leads`. The other records' names and captured details were never disclosed to a
  data principal asking what is held about them.
- **Fix (c81f2bc4f).** The document now also carries `leads`: every record, newest first.
  `lead` is unchanged, so existing readers keep working. **This is a wire-shape change**:
  `apps/web/src/lib/api/openapi.json` was regenerated with `check_openapi_fresh --write`,
  and `schema.d.ts` with openapi-typescript 7.13.0. There are no web fixtures of the type.
- **Test.** `test_a_subject_export_discloses_every_lead_record_not_only_the_newest` failed
  before the fix (`[] == ['Ravi Kumar', 'Ravi']`).

## Not fixed

- **Z9-N1 (P2, frontend flow, outside the lane).** The rights desk marks an erasure request
  `answered / erased` as soon as the erasure is FILED:
  `apps/web/src/app/c/[slug]/data-rights/page.tsx:169-173` closes it in the erasure
  drawer's success callback. `rights_desk._assert_erasure_answers` checks the linked
  request's subject, not that it completed. A stuck erasure then leaves the desk showing
  "answered", and the 90-day rights reminder stops counting it. Z9-01 removes the stuck
  case. Refusing an incomplete link server-side would break that web flow. The proper fix
  closes the desk row when `execute_deletion_request` completes; it needs a frontend change
  and a decision on the desk's meaning.
- **Z9-N2 (P3).** Global (`scope='global'`) DNC entries are never pushed to any client's own
  ThinnestAI workspace list (`engine_dnc.queue_engine_dnc_push` and the workspace backfill
  `workers/engine_workspaces.py:185` read tenant rows only). Every dial we place still
  refuses them at `check_dispatch`, so this only affects defence in depth at the platform.
- **Z9-N3 (P3).** Tenant erasure's job has the same unlocked first read
  (`execute_tenant_erasure`). A concurrent copy would fail on the `organizations.deleted_at`
  rowcount invariant and roll back, rather than overwrite, so this was left alone.
