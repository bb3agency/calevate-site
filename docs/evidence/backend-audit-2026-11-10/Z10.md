## Findings fixed

### Z10-01 (P2): the protective-slowdown reason was required, promised to the next reader, and stored nowhere
- `apps/web/src/app/admin/ops/LoadShedPanel.tsx` (the Reason field) tells the operator
  "Whoever finds the platform slowed reads this to decide whether the condition still holds".
  `apps/api/ops/routes.py::set_platform` sent the reason only to `write_audit`'s `summary`.
  That summary goes to the log stream: `audit_log` has no summary column, as the route's own
  docstring says. `PlatformStateOut` had no field for it either. An operator who finds the
  platform in `reduced` or `emergency` therefore cannot tell why, or whether it is still
  needed, and the likely next step is to lift a shed that is protecting the database.
- Fix: the reason is stored and shown. It follows the same contract `halt_reason` has with
  `outbound_halted`:
  - `core/loadshed.set_platform_status(load_shed_reason=...)` writes it in the same UPDATE
    as `load_shed_mode`.
  - It is NULL on `normal`. It is also NULL when the writer gives none, as when a
    maintenance window flips the mode, so a reason never sits beside a mode it did not
    explain.
  - `ops/service.read_load_shed_reason` returns it only while the row's mode is the one
    being shown.
  - `PlatformStateOut.load_shed_reason` carries it on the wire.
  - `LoadShedPanel` prints "Reason on the record: …", or "none was recorded with this
    change.", in the same words as the halt panel.
  - A halt request leaves the slowdown reason alone, just as a shed request leaves the halt
    reason alone.
- Test: `test_the_slowdown_reason_is_kept_and_shown_until_the_platform_returns_to_normal`.
  Web: `apps/web/tests/ops.test.tsx` gains "shows why the platform was slowed…" and "says a
  slowdown carries no reason…".
- Known limit, stated rather than hidden: when a maintenance window ends, `_complete`
  restores the earlier mode with no reason, so a `reduced` set before the window comes back
  reading "none was recorded". Keeping it would need a second column on
  `platform_maintenance_windows`. That is not worth a second migration for a window that
  opens over a shed.

### Z10-02 (P2): a WhatsApp account whose template seed failed could never submit them again (spent outbox key)
- `apps/api/whatsapp/signup.queue_templates` keyed `enqueue_outbox_once` on
  `whatsapp-templates:{account_id}`, and outbox keys are spent forever.
- `templates.seed_standard` deliberately leaves `templates_seeded_at` NULL when any
  submission fails. Its comment reads "so the account's next setup step
  (`accounts.finish_setup`) seeds again". `accounts.finish_setup` does call `queue_templates`
  when `templates_seeded_at` is NULL, but the insert hit the spent key and queued nothing.
- Nothing else resubmits these templates. `seed_whatsapp_templates`' own alert says so.
- Result: Calevate's standard templates show "Not sent to Meta" forever. They are the
  in-call WhatsApp follow-ups, so a client who connected WhatsApp during a Graph 5xx never
  gets them.
- This is the same class as the two production bugs named in the brief (business copy, KYC
  decision).
- A second gap: for a `connected` account, the client screen offered no control at all
  ("Finish set-up" shows only for `needs_attention`).
- Fix:
  - `queue_templates(again=True)` goes through plain `enqueue_outbox` for the
    `finish_setup` retry. A second seed beside the first submits nothing twice:
    `insert_template` hands a row back only while it is `submit_failed`, under its
    ON CONFLICT row lock.
  - `Templates.tsx` shows "Some standard messages did not reach Meta. [Send them again]"
    when one of Calevate's own templates for this account is `submit_failed`. The button
    calls the existing `/finish` route.
- Test: `test_finishing_set_up_after_a_failed_template_seed_queues_the_seed_again`. Before
  the fix: one outbox row. After: two.

### Z10-03 (P3): one account raising stopped the call-translation backfill for every account
- `apps/workers/call_translation.backfill_call_translations` was the only `resumed_walk`
  loop in `apps/workers` with no per-account `try`.
- `fleet_walk.resumed_walk` walks an item whose body raised first again on the next pass, so
  a persistent error for one account (in `_settle_interrupted` or `_untried_candidates`)
  aborted every tick at that account. No other account's untranslated calls were queued
  again.
- Fix: such an account is logged (`call_translation_backfill_tenant_failed`, ids only) and
  skipped, as in every other walker.
- Test: `test_one_account_that_raises_does_not_stop_the_translation_backfill_for_all`.

## Checked and found sound (not re-reported)
- Every `enqueue_outbox_once` caller (37) was read for a key that can block a legitimate
  later job:
  - `agent-fields:{agent}`: applies only to an untouched starter, so once is right.
  - `campaign-escalation:{contact}`: once per contact is intended.
  - `follow-up-drive:*`: the minute tick re-drives due runs anyway.
  - `agent-move:*`: the hourly tick passes its own suffix.
  - `dispute-outcome:*`: keyed on phase and status.
  - `hot-facts:{tenant}:{day}`: knowledge changes use plain `enqueue_outbox`.
  - The X3-noted fingerprint keys remain the open P3 recorded in round 4.
  - `opening-notices:*` was read only. It is notice machinery and stays hands off.
- Load-shed exemptions: every inbound webhook (Razorpay, KYC, Meta, lead sources) is under
  `/hooks`, so none is shed. `/v1/ops`, `/v1/admin` and the four login steps stay reachable.
- Outbound webhook retries:
  - Each attempt gets its own arq job id.
  - "Send again" CASes on `failed`.
  - The claim lease (15 min) is longer than `job_timeout` and the result window.
  - The tenant comes from the original payload, so I found no wrong-tenant path.
- `in_call_once`: claim, wait, reclaim are sound.
- Lead push `_sent_to_leadsquared`: the global outbox is joined through RLS'd tables, so it
  stays inside the tenant.
