## Fixed

### Z7-01 (P1, money and a stuck job) A "Fix them first" that lengthened a step's instruction crashed the job after the model was paid
- Where: `apps/api/agents/script_proposals.py::kept_to_paths`. It is called from
  `apps/workers/script_proposal.py::draft_script_proposal`, outside any guard.
- Cause: a fix takes only the lines the check named from the written script. A step's
  `instruction` and its `sounds_like` share one 600-character step detail
  (`ConversationStage._detail_fits_a_step`, `call_script.py:671`).
  - The usual repair for "no step asks for X" makes the instruction longer, and the
    `script` finding allows every instruction to change. The owner's `sounds_like` is kept
    beside it.
  - Together they went over 600, so `CallScript.model_validate` raised.
- What went wrong:
  - The model had already answered, and the draft got no meter row (hard rule 7).
  - The proposal stayed `drafting`, already claimed, until the ten-minute stale note "could
    not be finished".
  - Asking again could hit the same crash.
- Fix: a step that no longer fits takes the written step's instruction and `sounds_like`
  together, since they fit together there. If even that pair does not fit, the step stays as
  the owner wrote it (`_fit_step_details`).
- Commit: b7733de13.
- Tests, in `tests/fix_detail_overflow_2026_11_10_test.py` (all three red on 565a03ff2 with
  the ValidationError):
  - `test_a_longer_instruction_beside_the_kept_line_is_not_a_crash`
  - `test_a_pair_that_cannot_fit_keeps_the_owners_step`
  - `test_the_job_stores_the_fix_and_meters_it`

### Z7-02 (P2, money) A repair pass that could not be used dropped its spend from the meter
- Where: `apps/workers/script_proposal.py::_fixed_further`. This is in the loop rebuilt by
  901681f27. I left its design as it is.
- Cause: after a repair pass was paid and added to `spends`, `kept_to_paths` and
  `fix.targeted` ran unguarded. If either raised, the caller's
  `except Exception: _Repaired(drafted, [], [])` replaced every pass's spend with none.
- Fix: those two calls now sit inside the loop's guard. The loop stops and returns the spends
  it has.
- Commit: ada3ed43d.
- Test: `tests/fix_detail_overflow_2026_11_10_test.py::test_a_repair_pass_that_cannot_be_used_is_still_metered`.
  It was red on base: 1 of 2 paid passes metered.

### Z7-03 (P3, user-visible) Business examples: a refresh in progress showed the last run's failure
- Where: `apps/api/tenancy/business_copy_routes.py::render`.
- Cause: `stop_reason` and `stop_message` were returned while a run held the row.
- What the owner saw: they pressed "Refresh now" and read "Pip is writing them now" next to
  the previous run's message, for example "Not refreshed: AI help could not be reached" or
  "allowance used up".
- Fix: both are None while a run is in progress. The admin panel uses the same `render`, so
  it shows nothing failed during a run and the outcome once the run ends.
- Commit: 726aec01c.
- Tests, in `tests/business_copy_running_state_2026_11_10_test.py`:
  - `test_a_running_refresh_hides_the_last_runs_failure`, red on base.
  - `test_the_failure_is_shown_once_no_run_is_in_progress`.

## Not fixed (reported)

- **UNVERIFIED, a policy question. Pip memory distillation is charged to the client's AI
  allowance with no allowance gate.**
  - `workers/copilot_memory._distil_group` records `copilot_memory_distillation`. That
    feature is not in `ABSORBED_ASSIST_FEATURES`, so `read_ai_quota` counts it.
  - The sweep checks only the platform brake, never `require_ai_assist`. So hourly
    background work nobody asked for keeps adding to an account's usage after it reaches
    its ceiling.
  - I found no decision saying whether this is meant. It needs the founder's word: absorb
    it, or gate it.
- **By design, observed.** The text of a script change typed into Pip goes to the Sarvam
  standby unmasked when the paid legs fail (`script_assist._json_via_sarvam`).
  `script_assist`'s module note classes it as tenant-authored business content (D-127 G-2),
  not caller PII. Pip's own standby leg is masked (`service.masked_messages`).
- **P3. A suggestion the owner discarded while it was drafting is still charged.**
  `draft_script_proposal` meters every spend even when `store_ready` returns False because
  the request was discarded. D-819's `unused` flag is for answers the client did not get.
  Whether a person who cancelled should pay is a policy call, so I made no change.
- **Outer guard around `_fixed_further`.** On a crash it stores `left=[]`, so "Still to fix"
  would be missing. Z7-02 makes that path unreachable for the only calls that could raise
  after a paid pass.
