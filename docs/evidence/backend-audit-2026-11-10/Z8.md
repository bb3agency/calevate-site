# Z8: knowledge and files (backend audit, 10 Nov 2026)

Lane Z8, redis db 8. Scope: `apps/api/kb/**`, `apps/workers/kb_ingest*`, `kb_read`,
`apps/api/retrieval/**`, object storage for knowledge uploads, and the knowledge-to-script
suggestion trigger (`suggest_scripts_from_document`).

Test file: `tests/audit_2026_11_10_z8_test.py`. All three FIXED findings fail on the code
before the fix (run in the lane container; outputs in the commit body).

## FIXED

### Z8-01 (P2): a new note, file or link called "Facts you taught" replaced every taught fact

- Where: `apps/api/kb/service.py` `submit_source` and `apps/api/kb/uploads.py`
  `name_for_new_item`. A name is its own version sequence (`insert_source_version`). Only
  rename and remove refused the taught-facts source's name (`kb/store.py:766,798,836`).
  Creating something new with that name did not.
- What went wrong: an owner who typed a note (`POST /v1/kb/sources`) with that name got
  `201`, `version: 2` of the taught-facts source, approved and queued to publish. When it
  published it archived the compiled facts, so every agent lost all unpinned taught facts
  and answered from the note instead. The next fact taught then archived the note. A file
  upload or link with a given name (the Replace path, D-975) did the same. So did Pip's
  `knowledge_note_save`, through the same `submit_source`.
- Fix: `kb.service.refuse_reserved_name` gives 409 `kb_name_taken`, the code rename
  already uses. `submit_source` calls it unless `facts_source=True`, and only
  `teach/facts._republish` passes that. `name_for_new_item` calls it for uploads and links.
- Test: `test_nothing_new_may_take_the_taught_facts_name`. Before the fix: `assert 201 == 409`.

### Z8-02 (P3): an owner's file whose first reading raised was left waiting for a review it never needs

- Where: `apps/workers/kb_ingest.py` `ingest_kb_source`. arq only retries on `Retry`,
  `RetryJob` or a cancel, and this job raised nothing of the kind.
  `storage.StorageUnavailableError` is already a `Retry`. Any other fault while reading
  finished the job after one attempt: a dropped database connection, or a reader or
  picture-reader exception.
- What went wrong: the sweep then re-drives the row with `may_self_approve=False`
  (`sweep_kb_uploads`: "A re-drive NEVER approves anything"). It reads the file again, which
  is a paid model call for a photo, and then stops at `awaiting_review`. An account member's
  Word, Excel, text or photo upload then shows "Read it and confirm" and reaches no agent
  until somebody presses it. D-658 says such an upload is never reviewed.
- Fix: when the job may approve, any non-`Retry` fault is raised as arq `Retry` (waits
  30 s, then 120 s) until `WORKER_MAX_TRIES`. The original payload, and its approval, comes
  back each time. An existing `Retry` keeps its own wait. The sweep's in-process call
  (`may_self_approve=False`) behaves exactly as before. After the last try the fault is
  raised, and arq's terminal alerter reports it.
- Tests: `test_an_owners_file_whose_first_reading_raises_is_retried_not_left_for_review`
  (before the fix: `ConnectionResetError` escaped instead of `Retry`), and
  `test_the_last_attempt_raises_the_fault_itself`.

### Z8-03 (P3): re-reading a file we already hold suggested it to every agent's script again

- Where: `apps/workers/kb_ingest.py`, the end of `ingest_kb_source`, called after
  `reparse_kb_upload`. When `structured_text.PARSER_VERSION` changes, the sweep re-reads
  every live text upload. A reading that differs becomes a new version with a NEW upload id
  and the same `original_sha256`. Its publish called `queue_document_suggestions` for that
  new id, and the suggestion is de-duplicated only per upload id.
- What went wrong: every parser change sent every agent of every tenant holding a Markdown
  file a script suggestion for a file they already had. It also replaced or extended any
  waiting knowledge proposal, and cost one paid script-writer call per agent. An onboarding
  document escaped its exclusion as well, because `first_runs.document_ids` holds the old
  upload id.
- Fix: `_SAME_FILE_WAS_LIVE_SQL`. No suggestion is queued when an earlier published version
  of the same name had a file with the same digest. A different file is still suggested,
  and so is the same file re-uploaded after a removal (the removal deletes the old rows).
- Test: `test_a_file_read_again_is_not_suggested_to_the_scripts_a_second_time`. Before the
  fix, the new version's upload id was in the queued suggestions.

## Checked and sound (not re-reported)

- Link fetching (`kb_ingest._fetch_page`): every hop passes `assert_public_http_url`.
  Redirects are followed by hand, with at most 3. `egress_client` checks the address again
  at connect time (`_VettingNetworkBackend`), which stops a rebinding. The body is streamed
  with a 2 MB cap, and one deadline covers the whole chain. URLs are vetted at submission too.
- Uploads: the 20 MB ceiling is enforced before storage. The extension decides the kind,
  and the stored Content-Type is ours. A PDF must carry `%PDF-`. Object keys are built from
  ids only (`kb-uploads/{tenant}/{upload}/`). The presigned GET lasts 300 s. Every read
  route is under RLS, and an unknown id gets 404. Removal withdraws the vendor copy before
  deleting our rows. Objects are deleted by prefix after the commit, through the outbox.
- Replace and publish: the new copy is attached before the old one is withdrawn. Earlier
  versions are archived. `_DEACTIVATE_SQL` takes superseded chunks out of `kb_chunks`, and
  the retrieval epoch moves on count, version, embeddings and the last write. pgvector
  queries restate `tenant_id` and `is_active`.
- "Name (2)" (D-975): an advisory lock per tenant on names, and suffixes kept within 120
  characters. Concurrent same-name versions are serialised by `kb:submit:` locks.
- Earlier-round items remain fixed: reading budgets and stale-read settling (T3-02), the
  pypdf floor and signature check (secd), and the link sweep reading through a tenant
  session.

## NOT FIXED

- A link removed while a re-read version is queued can come back (UNVERIFIED, narrow
  window). `_recheck_link` can approve and queue v3 of a member's link. If the owner removes
  the live v2 before that job runs, v3 still publishes, because `remove_upload` deletes only
  the version it was given. I did not reproduce it. A fix would be to withdraw the later
  queued versions of the same name on removal, which changes what "remove" means for a
  versioned item. That needs the founder's word on removal semantics.
- Known and still open, from the secd lane (29 Oct): the OOXML expansion ceiling is 256 MB
  per document, and workers have no `mem_limit`. Unmeasured. Also, a member-linked page that
  changes is re-published without review. That was a deliberate decision (D-658).
- No migration. No change to the wire shape: a new 409 path reuses the existing code
  `kb_name_taken`, so the OpenAPI file was not regenerated.
