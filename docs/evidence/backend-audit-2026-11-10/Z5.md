## Fixed

### Z5-01 (P2): a new invitee could not "Accept with Google" while self-serve signup was closed

- Where: `apps/api/authn/google.py::finish` (the `if not signup_open` refusal, ~line 507) and
  `apps/api/authn/self_serve_routes.py::google_complete` (~line 197).
- Scenario: the invitation page (`apps/web/src/app/(auth)/auth/accept-invitation/page.tsx`)
  shows "Accept with Google" on every deployment where Google sign-in is configured.
  `self_serve_signup_enabled` defaults OFF (R-11). A person invited by an owner, with no
  Calevate account yet, presses it. `google.finish` ran BEFORE the invitation was looked at
  and refused with 401 `no_account_for_google`, whose remediation reads "Use the invitation
  your workspace owner sent" — while they were holding that invitation. The only way in was
  the password form on the same page, which nothing told them to use.
- Fix: `invitations.invited_address(token)` reads the address of a still-redeemable
  invitation (read-only, under `invite_session`, the same widening the accept paths use).
  The route passes it to `google.finish(invited_email=...)`, which creates the account when
  signup is open OR the invitation is addressed to the very address Google vouches for
  (still only after the existing `email_verified` and `_google_is_authoritative` checks).
  An invitation to a different address changes nothing. The burn and membership are still
  `accept_for_verified_address`, unchanged.
- Tests (`tests/self_serve_account_test.py`):
  - `test_an_invitee_accepts_with_google_while_self_serve_signup_is_closed`: end to end
    through `/v1/invitations`, the mailed token, `/google/start` and `/google/complete`.
    FAILED on the old source (401 from `/v1/auth/client/google/complete`), passes now.
  - `test_an_invitation_to_another_address_opens_nothing_while_signup_is_closed`.
- Commit: the one commit on this branch whose subject starts "A new invitee can accept
  with Google".

## Verified sound (read at source this session)

- Sessions (`authn/sessions.py`): reuse detection revokes the family in a transaction the
  refusal cannot roll back; rotation is a CAS that carries the absolute bound; the idle slide
  is guarded on `revoked_at IS NULL AND superseded_at IS NULL`; the stream check
  (`session_still_live`) never slides or revokes.
- Emailed tokens (`authn/tokens.py`): redemption is a CAS on `used_at IS NULL AND
  expires_at > now`; reset confirm checks the realm, invalidates the rest and revokes every
  session in the same transaction as the password; a policy-refused password rolls the burn
  back.
- OTP (`authn/otp.py`): accept and wrong-guess paths both count; Redis budget in front.
- Invitations (`authn/invitations.py`, `admin/service.accept_invitation`): advisory lock and
  re-read in the burning transaction (V1-03); D-974 first-password proves the address;
  reclaim only for unproved legacy rows; existing proved accounts need their own password,
  metered by the password budget; account-open checked before any credential write.
- Operator setup (`authn/bootstrap.confirm_bootstrap`, `operators.reissue_setup_link`):
  refuses an account that already has a password on both halves.
- Members (`tenancy/members.py`, `tenancy/routes.py`): self-action refused, last owner
  kept under `lock_owner_ids`, role change is a CAS on `expected_role` (so
  `expected_role: owner` cannot skip the promotion code), owner invite and promotion need a
  client action code bound to slug and address/person, Pip's team tools build the same codes,
  `org.membership` withheld from view-as.
- Client principal (`core/auth._load_client_principal`): liveness and membership re-read on
  every request under `user_session`; closed and churned accounts refused.
- D-976 mobile number: client cookie only (view-as gets 401), one locked statement,
  audited without the number.
- Google (`authn/google.py`): state bound to an HttpOnly browser nonce, single-use `jti`,
  PKCE, nonce, `iss`/`aud`/`azp`/`exp` checked; `safe_next` refuses `//`, `/\` and schemes.
- CSRF: every auth route calls `enforce_same_origin`, which checks `Origin` even on
  `same-site`.

## NOT FIXED / UNVERIFIED

- P3, `google_complete`: when the invitation in the request is no longer redeemable,
  `google.finish` has already signed the person in (and, with signup open, created their
  account), then `accept_for_verified_address` raises `invitation_invalid` and no cookie is
  set. The refusal itself is right; the account it left behind is harmless (a verified
  Google account with no membership). Not changed.
- P3, `confirm_password_reset` burns a token presented on the wrong realm's endpoint
  (redeem is not filtered by realm; the realm is compared after). Reachable only by hand-
  crafting a request with your own token. Not changed.
- P3, stale docstring: `admin/service.resend_invitation` still says redemption does not mark
  the address proved (D-185); D-974 changed that. Comment only, left for the owning lane.
- Self-serve signup lets one signed-in person create several businesses (5 an hour per
  identity), each with its own free trial. The quota comment says this is intended ("an
  office ... can onboard several sites"); recorded, not a defect without a founder ruling.
