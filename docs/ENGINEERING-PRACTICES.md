# Calevate — Engineering Practices & Executable Governance

Version 1.0 · July 2026 · Decision D-29. Sources: the raghava-organics production
repo's guardrail system (~20 drift/parity/discipline checks in CI — the proof that
this style works for a tiny team) + 2026 industry practice (fitness functions,
trunk-based development, coverage ratchets).

Principle: **rules that matter are executable.** A Hard Rule enforced only by memory
or review will be violated exactly when the codebase grows fastest. Every check below
is a script in CI; docs describe them, they don't substitute for them.

## 1. Git workflow (D-29)

- **Trunk-based**: short-lived branches (hours–days), merged to `main` daily;
  `main` is always deployable (CD deploys it on green CI). No long-running branches.
- **Conventional Commits**, hook-enforced: `feat:` `fix:` `docs:` `refactor:`
  `test:` `chore:` `ci:` — scope optional (`feat(crm): …`). Machine-readable history
  feeds changelogs and makes `git log --oneline` a project narrative.
- **Pre-commit hooks** (`.pre-commit-config.yaml`): ruff check+format on staged
  files, commit-message lint. Fast (<2s) — anything slower belongs in CI, not hooks.
- Small changesets; a PR (even self-reviewed) for anything touching auth, billing,
  or compliance modules — mirrors SEC-COMP §5's two-person-review-while-team-of-2
  self-review checklist.

## 2. The guardrail pack (Calevate's fitness functions)

Adapted from raghava's checks to OUR hard rules. **Critical four ship in M1** with
the first real code; the rest land incrementally with the milestone that creates
what they guard. All run in `make check` + CI; a red guardrail blocks merge.

### Critical four (M1)

| Check | Enforces | Mechanism |
|---|---|---|
| `check:engine-isolation` | Hard rule 2 — only `engine/` sees vendor SDKs/payloads | **import-linter** (`make guardrails` → `lint-imports`), 2 contracts SHIPPED and passing, both in `pyproject.toml`: (1) `calevate_shared` imports no `apps.*`; (2) no business module may **directly** import a VENDOR ADAPTER — `forbidden_modules` is `apps.api.engine.bolna` / `apps.api.engine.fake`, **not** `apps.api.engine`, and `allow_indirect_imports = true`. That narrowing is deliberate: hard rule 2 is about vendor PAYLOAD SHAPES, not about the word "engine". Workers and business modules legitimately need an engine (the post-call pipeline and the reconciliation poller cannot exist without one, TRD §8) — they reach it through the `apps.api.engine` factory, which hands back the `VoiceEngine` Protocol and normalized models. A factory necessarily imports its adapters, so banning the transitive chain would ban having a factory; what leaks a vendor shape is a module NAMING an adapter in its own imports, and that stays banned. Add each new business module to `source_modules` (currently `admin`, `agents`, `billing`, `campaigns`, `compliance`, `core`, `crm`, `ingest`, `integrations`, `kb`, `ops`, `reliability`, `tenancy` under `apps.api`, plus `apps.workers`). The voice-runtime twin is enforced by its own deploy boundary. |
| `check:rls-coverage` | Hard rule 1 — every tenant table has FORCEd RLS | script queries `pg_tables`⨝`pg_policies` in the CI database after `alembic upgrade head`; any tenant_id-bearing table without a FORCEd policy = fail |
| `check:redaction-exposure` | Hard rule 5 — raw transcript text never in default responses | serializer-exposure scan: any Pydantic response model exposing `text` (vs `text_redacted`) outside the role-gated endpoints = fail (raghava's `serializer:exposure-check` pattern) |
| `check:env-parity` | fail-fast config doctrine | `.env.example` keys ⟷ `calevate_shared.config.Settings` fields, both directions; drift = fail |

| Check | Lands | Enforces |
|---|---|---|

| `coverage:ratchet` | **SHIPPED** (`scripts/check_coverage_ratchet.py`; `make coverage-ratchet` runs the suite under `coverage run` and then scores it, `make check` calls that INSTEAD OF `make test`, and CI's existing test step gained the instrumentation — ONE suite run, never two) | D-29's words are "coverage ratchets not targets"; BACKEND-PATTERNS §9 says where: "scoped to the HIGH-RISK surfaces … rather than a repo-wide number". Both are literal here. **The unit is a COUNT of uncovered units — statements never executed, plus branches taken in only one direction, plus `# pragma: no cover` exclusions — per HARD-RULE SURFACE.** Not a percentage: "the number of bugs is not a function of the *percentage* of uncovered code, but rather the *amount*" (coveragepy#815), and a percentage moves when you delete a covered helper or add 400 covered lines beside an untested branch. Six areas, one budget each, each naming the rule it protects — `tenancy-session` (rule 1), `compliance-gate` (5), `dial-path` (5), `ledgers-and-money` (4+7), `redaction` (5+6), `voice-runtime-ack` (3) — because a single repo-wide number lets coverage bought in a serializer pay for a branch lost in the dispatch gate, and the aggregate never moves. Branch coverage, not line: every rule guarded here is a rule about the branch NOT taken, and a line-only run is satisfied by executing the `if` once. **The gate is an EQUALITY, and that is what makes it a ratchet rather than a target**: above budget is a regression; BELOW budget also fails, because an improvement nobody locked in is headroom, and headroom is where the next deleted test hides (#815's second half — "contributors will have to update the number … to lock in the newer, lower number"). One consequence worth knowing: a budget that is merely EDITED UPWARD fails on the very next run by itself. Raising one is possible and deliberately loud — a `RAISED_BUDGETS` waiver in the script carrying the ceiling, the reason (≥80 chars) and what closes it; `--update-baseline` refuses to write a bigger number without one, `stale_waivers()` deletes it the moment the area improves past it, and `tests/coverage_ratchet_guard_test.py` pins the set so a new waiver costs a diff in a test too. **The area list stays honest by DERIVATION, not memory**: `required_surfaces()` reads the live `APPEND_ONLY_TABLES`, the modules that EXECUTE the tenancy GUC (off the AST, docstrings excluded — a grep matches four modules whose only mention of it is a comment about it), the `Numeric` money columns, `check_compliance_invariants.dial_sites()`, the redaction primitives resolved by import, and every file under `apps/voice-runtime`; a hard-rule surface in no area FAILS the gate. It earned that on its first run, adding two dial surfaces the hand-written list had missed — `crm/routes.py` (the D-21 lead button and callback) and `ingest/service.py` (the instant-lead webhook). It also REFUSES TO SCORE a run it cannot vouch for — a distinct third outcome (exit 2; a verdict-shaped failure is exit 1, both red) rather than a verdict it has no standing to reach, because reporting an artefact as a regression is how a guardrail teaches people to re-baseline past it. Two halves: the REPORT (no branch data, a measurement older than the code, an area matching no file, an area with zero executed statements) and the RUN. The second is evidence, not a flag: the suite is started with `-p scripts.check_coverage_ratchet`, the gate's own pytest plugin, which records into `.coverage-run.json` beside the data file what the run consisted of — outcomes, deselection and every selection option in force, collection errors and module-level skips, whether Postgres and Redis answered a probe at `pytest_sessionstart`, and whether any tenant-scoped table (off the live `TENANT_TABLES` registry) held rows BEFORE the first test. Any of those and the gate scores nothing, and `--update-baseline` writes nothing, which is the half that matters because the baseline file is where a wrong number enters the repo. That last check is the one with history: this gate failed CI twice on a two-unit delta, both times because the committed baseline had been measured against a lived-in dev database and both times "fixed" by copying CI's number into the fixture — so the rule "run `make db-reset` first" stopped being a comment and became a refusal. What it deliberately does NOT gate on: the skip COUNT, which legitimately differs between a laptop and CI; the counts and the commonest reason are printed with every verdict instead, and the two causes that actually bit us (a service down, a dirty database) are detected at their source. **Measured cost** (this machine, same tree, both runs contended by other work so read them as a ratio, not a clock): the suite is 1110s uninstrumented and 1637s under `coverage run` — about +45%, one run either way. It does not double the suite, which is the constraint that decides the placement: the gate lives in CI's existing test step and in `make check`, and `make test` stays clean for the dev loop. `COVERAGE_CORE=sysmon` would cut most of that overhead and is NOT usable here — "In Python 3.12 and 3.13, it does not support branch coverage" (coveragepy `doc/config.rst`, `[run] core`), and this repo is pinned to 3.12; it becomes a one-line change on 3.14, where sysmon is the default. The check itself (loading the data, reporting, deriving the surfaces) is ~5s. **Baseline as seeded** (2026-08-12): tenancy-session 5 uncovered (96.2% of statements+branches), compliance-gate 70 (94.5%), dial-path 123 (80.2%), ledgers-and-money 49 (95.0%), redaction 13 (94.1%), voice-runtime-ack 24 (92.6%). Two of those six were WRONG — `compliance-gate` is 68 and `voice-runtime-ack` 22 against a freshly migrated and seeded database — which is the measurement CI takes and the evidence behind the refusal described above. Four of the six were bit-identical across two independent full runs; the two that moved moved because the tree did — which is the metric behaving. Those numbers are a FLOOR, not a target, and the first act after any in-flight work lands is `make coverage-ratchet-accept` to click them down. Deliberately NOT: no percentage anywhere in the gate and no `fail_under`; no per-file budgets (every refactor would re-bless the baseline and nobody would read the diff); nothing on `apps/web` (its gate is `make web-check`, D-53); nothing on the engine adapters (the conformance suite is a stronger statement than a line count and `lint-imports` guards the boundary — one way per problem); and no claim that a covered branch is a TESTED branch, since no coverage tool can tell an assertion from a call. That last one is why the ratchet never demands a number the suite has not already earned: the initial budgets are simply what the tree measured on the day it shipped, so its first act rewards nobody |
| `check:docs-drift` | M2 — **SHIPPED** (`scripts/check_docs_drift.py`, in `make guardrails` and CI) | The docs are authoritative (CLAUDE.md), which is exactly why their MECHANICAL claims have to be executable: an agent reads the doc, runs the command it names, and gets `No rule to make target`. Four questions against the live `apps/web` tree: (1) every variable the package reads is declared; (2) every declared variable is read (the stale direction — a key that survives a refactor is configured in three environments and decides nothing); (3) no `NEXT_PUBLIC_` key is shaped like a secret (`_SECRET`, `_PASSWORD`, `_TOKEN`, a trailing `_KEY`), since nothing with that prefix is private — publishable keys are the legitimate case and each needs a `PUBLIC_BY_DESIGN` entry stating why the VENDOR calls it public, verified live so the registry can only shrink; (4) nothing reaches `process.env` in a form Next cannot inline (`process.env[name]`, a destructure, an alias — all `undefined` in the browser, all type-check clean). **The declarations live in `apps/web/.env.example`, a second file rather than a section of the root one**: the root file is checked both ways against `Settings`, so a real `KEY=` line there fails `check:env-parity` — which is precisely why the browser keys had been written as COMMENTS, a declaration no machine could read. ### Patterns deliberately adopted from raghava

- **Evidence artifacts**: DR drills, stress runs, and the engine-verification
  scorecard write JSON/markdown evidence committed to the repo — auditable history,
  and DPDP/client-facing proof material for free.
- **Contract-proposal flow** for config keys: new Ops-config/env keys go through a
  script that updates example + Settings + docs together (their
  `ops:config-contract-proposal`) — the anti-drift move is making the RIGHT way the
  EASY way.
- **`parity:scorecard`** idea: one command that runs every guardrail and prints a
  single pass/fail table — `make guardrails`.

### Explicitly NOT adopted (and why)

- **core-drift / core-sync / release-train** (their template-repo→client-repo
  versioning): Calevate is ONE multi-tenant product, not a repo-per-client agency
  model — there is no template repo to drift from. If a white-label tier ever
  un-defers (ROADMAP §7), this machinery is the reference.
- **Design-token contract check**: no cross-repo design system to protect yet.

## 3. Dev loop conventions

- `make dev` / `make check` stay the only two commands a session needs; every new
  routine task gets a Makefile target (discoverability beats memory). `make web-check` is
  the frontend third of `make check` and exists separately only so a frontend-only change
  can be gated without a database.
- Fixtures over mocks-of-our-own-code: fake-engine adapter for pipeline work
  (DEV-SETUP §3), golden-transcript fixtures for extraction, recorded Telugu
  utterances for the regression harness.
- Windows-first dev reality (this machine): scripts must run under Git Bash/cmd;
  no bash-isms in Makefile recipes that Windows make can't run; see the
  scaffold-gotchas memory for the uv/pnpm traps already found.
- AI-agent hygiene: rememory search before non-trivial work; store decisions after;
  the docs set is authoritative and drift-checked (see §2), so agents cite docs
  rather than re-deriving.

## 4. Release discipline trajectory

M1: green `make check` + guardrails = deployable; CD auto-deploys main (DEPLOYMENT §3).
M2: + regression harness red blocks promote (OPERATIONS §3 wiring); webhook-storm in CI.
M3: + error-budget release gating once Prometheus recording rules exist.
Always: migrations reversible, RLS in-migration, two-step column deprecation
(hard rule 8) — checked by `check:rls-coverage` and migration review.
