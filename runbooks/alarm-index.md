# Alarm index — every code this platform can raise

**MOST OF THEM NO LONGER REACH A PHONE, AND THAT IS D-591.** This file used to be titled
"every code that can reach a phone", and every code did — so four ordinary deploys'
`signal_received`, a visitor's browser extension tripping `csp_violation` and twenty-six
observations of one already-diagnosed `fx_rate_stale` arrived in the same inbox, looking
exactly like the operational failure in the same evening that was worth reading.

Every row now carries a **Severity**, and it decides where the alarm goes:

| Severity | Where it goes | What it means |
| --- | --- | --- |
| `page` | **Email**, and a console row | Wake a human now: money moved and did not land, a statutory or TRAI deadline is breached, data is unrecoverable or unreachable, a credential is unusable, or a whole client (or the whole platform) has stopped working. |
| `attention` | **`/admin/ops/alerts`** only | A real failure, bounded — one call, one client, one sweep, one retryable leg. Look at it today. This is where most genuine failures live. |
| `record` | `/admin/ops/alerts` only | Expected, or somebody else's noise: a normal deploy, a browser extension, an unauthenticated stranger's bad signature, a caveat on another alarm's count. |

`apps/api/core/alarm_severity.py` is the source of truth and `scripts/check_alarm_wiring.py`
fails the build when this column disagrees with it — so a row here cannot quietly promise
you a mail you will not get. A code with no severity at all defaults to `page`: loud, not
closed.

**A `page` MAILS ONCE PER EPISODE, NOT ONCE PER OCCURRENCE.** The onset is mailed; the
repeats are counted; a condition that goes quiet for an hour is closed and a one-line
CLEARED notice is sent. So a still-running incident is read on the console, not in the
inbox — and if it starts again after clearing, that is a new episode and it mails again.
The exception is a code in `REPEAT_WHILE_OPEN_S` (`apps/api/core/alarm_severity.py`): it
re-mails at that interval while its episode stays open, with `Still open:` in the subject.
Today that is `ai_provider_degraded`, hourly. A condition that can report its own recovery
closes its episode at once and the CLEARED notice says "the condition reported recovery".

You were paged. The subject line is
`[calevate/<env>/<service>] Action needed: <plain headline> (<code>)` (`Still open:` on a
reminder, `Cleared:` when it ends). The mail itself quotes this file's row for the code (its
"What it means" and "What to do" columns are read at send time, D-790), so editing a row here
changes the next mail. Find the code here: what it means in one line, and where to go next. If you were NOT paged and are
looking for what has been happening, open **`/admin/ops/alerts`** — every alarm of every
severity has a row there, with its count, when it started and whether it mailed.

**This file is checked, not curated.** `scripts/check_alarm_wiring.py` derives the alarm
vocabulary from the tree — every `alert()` call, every `ProblemError` carrying a
`failure_stage` (which `core/errors.py` relays into `alert()` verbatim), every `*_code`
field on an ack meter, and every alarm the host backup chain emits in shell — and fails CI
in **both** directions: a row here with no call site behind it, and a code that can page
somebody with no row here. It is in `make guardrails` and in CI.

**Read the stage first.** `ROUTE_HANDLER` = something arrived and was refused;
`CORE_LOGIC` = a decision inside the app; `OUTBOX_DISPATCH`/`WORKER_*` = the reliability
path; `PROCESS_RESTART` = a service going down; `BROWSER_RUNTIME` = it happened in a
VISITOR'S BROWSER and reached us only because the browser was told to report it, so the
place to look is a console screen and not a server; `HOST_BACKUP` = the host chain, outside
every Python process (OPERATIONS §4).

**Noise bounds apply to all of them.** One recording flush per `stage:code` per 15 minutes,
and — for the `page` rung, the only one that mails — 20 emails/hour globally with a burst
of 6; suppressed and dropped counts ride the next delivery (`apps/api/core/alerting.py`).
"Happened once" and "still broken, 199 times" look different — read the `note:` lines, or
read the occurrence count on `/admin/ops/alerts`, which counts every occurrence including
the withheld ones.

### Refusals that alarm because they are 5xx (the `ProblemError` class)

**These were always alarms and nothing could see them.** `core/errors.py` turns every 5xx
`ProblemError` into an `alert()` — its handler relays `alert(exc.failure_stage, exc.code)`
and `failure_stage` DEFAULTS to `ROUTE_HANDLER`. `check_alarm_wiring` only scanned the
sites that name a stage explicitly, so fifty codes raised through the default were
undocumented, unclassified, and therefore `page` by the fail-loud default — including
`rate_limited`, `too_many_attempts`, `service_load_shed` and `platform_maintenance`, which
are the highest-volume refusals in the product. The founder's inbox found this, which is
the wrong instrument. The scan now decides by the `kind` (the three 5xx kinds alarm; a 4xx
refusal is a conversation with a caller and alarms nobody).

## Metric names

Named recorders in `apps/api/core/alerting.py`. They are the vocabulary an SLO rule may
use; nothing else may emit a metric name (the guardrail fails on a direct
`metrics_log.info("metric", ...)`). There is no scraper yet — these are structured log
lines (DEPLOYMENT §8), so "read the metric" means searching them.

| Name | What it measures | Read it when |
| --- | --- | --- |
| `webhook_ack_ms` | The engine-webhook receiver's ack latency, against hard rule 3's 500ms budget. | `webhook_ack_slow` fired, or after a campaign burst. |
| `retrieval_ms` | One knowledge retrieval end to end, labelled `provider`, `tier` and `cached` (TRD §6). The label is on ONE series on purpose: hit and miss are two paths to the same answer under one budget, so the blend — what a question costs given this account's real hit rate — is the number worth reading, and the halves are still recoverable by filtering. | A client says the assistant is slow to answer questions about their own knowledge, or before changing anything about the cache: `cached=false` climbing is the store, `cached=true` climbing is Redis or the epoch read. |
| `inbox_handling_ms` | How long one inbound webhook event sat between being recorded and being handled — the receiver's own half of the reliability triad. | Leads or call records are late and `pipeline_lag_seconds` looks healthy: the delay is upstream of the pipeline, in the inbox. |
| `inbox_lag_seconds` | The age of the OLDEST unhandled inbox event at each dispatch tick. A rising floor means the drain is behind, not that one event was slow. | Read it beside `inbox_handling_ms`: handling fast + lag rising is a throughput problem, both rising is a dependency. |
| `pipeline_lag_seconds` | Hangup → lead visible, per stage. The 2-minute SLO. | `postcall_pipeline_stalled` fired, or a client says leads are late. |
| `speed_to_lead_seconds` | Web form submitted → outbound dial placed. FLOWS §4 targets < 60s. | A client says the instant callback is not instant. |
| `outbox_lag_seconds` | How long a side effect waited in the outbox before dispatch. | Anything downstream looks slow. |
| `outbox_dlq_depth` | How many outbox messages are dead-lettered right now. | `outbox_dead_letter` fired. Read beside the console's `deferred` count — the pair is the diagnosis. |
| `extraction_failures` | Post-call extractions that failed, by reason. | Leads are arriving empty. |
| `reconciliation_repairs` | Calls the poller had to fix, by kind. `missing_call` = a webhook we never got; `unfinished_pipeline` = our own bug. | A rising `unfinished_pipeline` is ours to fix. |
| `reconciliation_listing_incomplete` | Polls that could not promise they saw the whole window, by reason. | Any non-zero value means calls may have gone unseen. |
| `webhook_replay_divergence` | A settled transition re-delivered with different bytes. | Deliberately not an alarm. Investigate a sustained rate. |
| `compliance_blocks` | Dials refused by the gate, by rule. `complaint_spike`, `spend_cap`, `dnc`, `no_consent`, … | A campaign stopped and nobody knows why (`runbooks/campaign-stall.md` §8). |
| `campaign_dials` | Contacts rung per dispatch tick, with how many the gate blocked. | The pair is the signal: 0 dialled with 40 blocked is very different from 0 and 0. |
| `dispatch_tick_seconds` | How long one campaign dispatch tick took, against its 30-second interval. | `dispatch_tick_overrun` or `dispatch_tick_overlap` fired. |
| `live_publish_failed` | A live change note (D-774) that did not reach Redis after its write committed, labelled `reason`. The write stands; open browsers catch up on their next reconnect or safety poll. | Consoles feel slow to update. A run of these means Redis is unreachable from the api or workers, and every console has fallen back to polling. |
